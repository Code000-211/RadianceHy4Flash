# K-06 (deeper prefetch for 3-unit waves): CLOSED — the third resident weight unit costs more occupancy than the latency it hides

Item as written (backlog K-06, `notes/backlog/optimisation-backlog.md`): "`r4d_gemm_iqr.hip:184-186` (GEMV), `:411-417`
(m16), `r4d_gemm_fp8a8.hip:789-805`: a wave holds the current unit and one in flight; with nkb / KW <= 4 (q_a,
latent_in, shared gate_up: 3 units a wave; shared down: 2,2,1,1) issue all units up front (14 VGPR a u5 unit: 3-4 fit)."
Why: "those launches are latency-bound (K-01 table); est. ~1 us on 4-5 launches a layer." Verify: "kbench `gemm_iqr` /
`gemm_i8a8` rows at (1, 1024..1536, 3072), VGPR/spill report in the commit message". BI, effort S.

This branch built it — a three-unit ring (the wave's current unit plus two in flight) in all three loops — and measured
it on one served lane, with the stamps layer table and with the kernel benches. It reverts it: the targeted kernels are
**slower**, not faster, because the second lookahead unit pushes the decode forms over the `R4D_WAVES(6)` register cap.

## What the code says (at HEAD, after this branch's revert)

- The three loops each keep the current weight unit and one in flight, and shift at the end of the block's iteration:
  GEMV `r4d_gemm_iqr.hip:172` (`typename D::Raw cur, nxt;`), fetch `:194` (`nxt = D::fetch(c, rt, kb + KW, lane, true)`),
  shift `:298` (`cur = nxt;`); m16 the same at `:387`, `:429` (plus the token tile `bload(0u, kb + KW, bn, true)` at the
  same depth), `:491`; int8 kpar `r4d_gemm_fp8a8.hip:787` (`Stage8 ac[2], an[2];`), the unit-ahead fetch `:816`
  (`aload(un, an); bload(0u, un, bn);`, `un = h + 1u < kUG ? u + 1u : (g + KW) * kUG`), shift `:829`.
- The launch bound is what decides this item: both kernels carry `R4D_WAVES(6)` (`libr4d/r4d_common.h:39`, 1536 / 6 = 256 VGPRs), so the compiler
  must fit 1536 / 6 = **256 VGPRs** a thread. `libr4d/isa/res.sh` at HEAD gives the decode forms 147-240 VGPR (GEMV,
  8-9 waves), up to 248 (m16, 5-8 waves) and up to 230 (int8 kpar, 6-12 waves): the heaviest forms are already at or
  near the cap, and the item's own estimate ("14 VGPR a u5 unit: 3-4 fit") reads a VGPR count from forms that have
  room, not from the forms this model runs.
- At the launcher the short-K rows this targets are `kw = N >= 4096u ? 4u : 8u` with `nkb = K / kBlock`
  (`r4d_gemm_iqr.hip:967`, `kBlock` 128, `:46`). hy4-flash's trunk (`K` 1536, `N` 3072: q_a, latent_in, gate_up, ...)
  is `nkb` 12, so `kw` is 8 and a wave walks **two units (one, for its last four waves)**; the shared down arm is `nkb` 24
  at `N` 1536, so also `kw` 8 and **three units a wave**. At two units a wave a ring of three is never refilled at all.

## What was built and measured, then reverted

The ring, in the same shape at all three sites, so there is one loop body and no branch (the item offers 3-4 units
"up front"; a uniform depth keeps the code single-path and covers 2- and 3-unit waves alike):

- GEMV and m16: `typename D::Raw cur, n1, n2;`, after the chain wait (K-05's pre-wait unit untouched) the primes
  `n1 = D::fetch(c, rt, wave + KW, ...)` and `n2 = D::fetch(c, rt, wave + 2u * KW, ...)`, and at the block tail
  `cur = n1; n1 = n2; if (kb + 3u * KW < c.nkb) n2 = D::fetch(c, rt, kb + 3u * KW, ...)`. The m16 keeps the token tile
  at one unit ahead (`bload(0u, kb + KW, ...)`), since the item asks for the weight only and two activation units would
  cost another 16 VGPRs a unit.
- int8 kpar: `Stage8 ac[2], a1[2], a2[2];`, a `ustep(u, h, d)` index helper so the lookahead reads as "d units ahead
  in this wave's order" (`u + d + ((h + d) / kUG) * ((KW - 1u) * kUG)`, which reproduces the existing
  `h + 1u < kUG ? u + 1u : (g + KW) * kUG` at `d = 1`), the primes for `d = 1` and `d = 2` after the wait, the shift
  `ac = a1; a1 = a2;` and the refill `aload(ustep(u, h, 3u), a2)`. The activation (`bload(..., bn)`) stays one unit
  ahead at the top of the loop body.
- Both are BI by construction (the same units, in the same order, into the same accumulators); the only change is when
  the load is issued. A new `r4d_selftest` case at the item's geometry (`iqr_gemm_case(pl, f, 1, 1536, 3072)`,
  `iqr_gemm_case(pl, f, 16, 1536, 3072)`, `i8a8_numeric(pl, "gemm_i8a8_nt_m16", 1, 1536, 3072)`) was added with it; the
  first version of the ring refilled at `d = 2` instead of `d = 3` (one unit duplicated after the shift) and the i8a8
  case caught it at `rel_l2` 0.741 before any lane run was believed — the case is worth its lines if this is retried.

## Why it closes without code

The item's premise is that a 3-unit wave never refills its one-deep pipeline, so the extra units can only help. The
measurement says the price is paid elsewhere: a third resident unit is 14 VGPRs of the wave's `Raw` plus whatever the
allocator needs to keep it live across the unrolled block body (measured: +21 VGPR on average, +62 at worst), and on
RDNA4 with `R4D_WAVES(6)` that crosses 256 and costs a resident wave on two thirds of the GEMV forms — fewer
concurrent waves, so fewer weight streams in flight per SIMD, which is exactly the resource a latency-bound launch is
short of. Every targeted kernel is slower on both the served lane and the standalone bench, and the one arm that looked
faster (c1 tok/s +2.2 %) is contradicted by its own op (`iqr_gemv_kernel` 9.2 → 9.9 us); at hy4-flash's trunk shapes
`nkb` 12 with `kw` 8 walks two units a wave, so the ring's third slot is never refilled and its primes are pure cost.

The item stays worth an estimate in the backlog's model only if a variant pays for the units: a *launch-geometry* lever
(more units a wave at the same resident VGPRs, e.g. `kw` 4 instead of 8 at short K, `:967`) or a prefetch into LDS
instead of registers. Neither is this item as written, and neither is measured here.
