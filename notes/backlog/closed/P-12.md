# P-12 closed: the 64-/128-row levels are real, but the shortcut that reaches them is not safe

Closed without code, per CARDS.md §2's own alternative ("otherwise write `closed/<ID>.md` with the numbers and the
reason"). Measured on the house lane.

## What was tried

The item's change as written is two parts: lower the level floor from 256 rows, and round every transient's rows up to
the largest row tile of any kernel that writes it. Only the first part is reachable from today's core, so it was built
and measured alone, on `p12-levels` (a scratch branch, nothing pushed):

```c
lo = std::max<int64_t>(lo, 64);
for (int64_t R = lo; R < cfg_.max_tok; R = (R < 256 ? R * 2 : R * 4)) want.push_back(R);
```

That yields levels at 64 / 128 / 256 / 1024 rows instead of 256 / 1024.

## What the levels are worth

`I activation arena: lends …` for the two arms, same tree, same config, same lane:

| level | floor 256 (today) | floor 64 |
|---|---|---|
| ≤64 tokens | — | **2.60 GiB** |
| ≤128 tokens | — | **2.55 GiB** |
| ≤256 tokens | 2.44 GiB | 2.44 GiB |
| ≤1024 tokens | 1.79 GiB | 1.79 GiB |

So the item's estimate is right in direction and size: the small levels lend **+0.16 GiB at ≤64 rows** and +0.11 GiB at
≤128 — the "+60-90 resident units" the item predicted, at 2 MiB a unit.

## What it does not buy, and what it costs

Output parity holds — the same greedy completion on both arms is byte-identical (`md5 67b91aaa3d0c1983…`) — so the
shortcut does not visibly corrupt anything on this config.

But it is not measurably faster, and the two metrics disagree in sign:

| lane | floor 64 | floor 256 | delta |
|---|---|---|---|
| `c1` decode tok/s (median of 3) | 129.42 (98.33 / 129.42 / 146.01) | 130.48 (132.38 / 130.48 / 124.89) | −0.8% |
| `c8` decode tok/s (median of 3) | 276.35 (276.35 / 256.91 / 281.12) | 272.15 (272.15 / 259.05 / 286.59) | +1.5% |
| `c8` aggregate tok/s (median of 3) | 238.97 | 241.20 | −0.9% |

The `c8` decode figure is +1.5% and its aggregate is −0.9%; the control's own spread is 259-287. The item's stated case
is +0.3% at c8, which is under this lane's resolution (about ±8% between runs at c8, ±15% at c1).

## Why close rather than merge the shortcut

The floor is not convention: the comment above it (`core/engine_bringup.cpp:1814`) says a tiled kernel may write the
padding rows of its last tile, and 256 is a multiple of every tile, so padding never reaches the next buffer. A 64-row
level keeps that property only if the buffers are rounded up to the write tile — the item's second half — and core has
no write-tile metadata to round with: `RadBufDecl` (`abi/rad_builder.h:454`) has no tile field, no kernel publishes
one, and nothing in `core/` carries `row_tile`/`write_tile`. The 64-row level's own size (91.26 MiB against 257.57 MiB
at 256) proves the plugin shrinks its declared shapes rather than padding them, which is exactly the case where a
kernel that pads would write past the buffer's declared extent.

One byte-identical greedy completion is not evidence that no kernel in the tree pads at that level, and the payoff being
defended is 0.16 GiB whose e2e effect is inside noise. So the item stays closed with this note; the safe form needs the
tile metadata first.

## What would reopen it

- A per-buffer write tile in the plugin ABI (trailing, zero-defaulted field, as `kv` was added), published by the arch
  plugins and used by `plan_level` to round transients up. Then the floor can fall without the padding argument.
- Or a c8 lane with a spread tight enough to resolve +0.3%, which would tell us whether the 0.16 GiB is worth having at
  all once it is safe.
