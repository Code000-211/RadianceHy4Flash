## What the branch built

`libr4d/r4d_mla_sink.hip`, +108/-16. The stash already writes the chunk's latent rows into `keys` (`kPitch` 584) for the
score side; it now writes the same values a second time, transposed, into `__shared__ uint16_t vt[512][16]`
(column-major: `vt[col][token]`), and the value product reads that tile through `frag(vt, kVToks, colbase, 0, lane)` —
two `ds_read_b64` a lane a fragment instead of eight `ds_read_u16`.

- **The transposition costs no global traffic.** A chunk's 16 tokens are staged in halves of eight, one thread a half
  (`tid & 63` = the column piece, `tid >> 6` = the half), and such a thread already holds its eight tokens' column
  pieces; the transpose is an 8x8 u16 register transpose, 32 `v_perm_b32` a thread, `perm(a, b, sel)` taking its low
  16 bits from the *second* argument so one `v_perm_b32` yields two adjacent tokens of a column.
- **Two `ds_read_b64`, not the item's one `ds_read_b128`.** The b128 needs the tile's tokens in the fragment's own order
  (0-3, 8-11, 4-7, 12-15 a column), which splits each half's eight tokens into two four-token runs: the stash would then
  store two 8-byte pieces a column instead of one 16-byte one, 32 more wave-instructions a chunk over the staging
  threads — exactly what the read side would gain. Natural token order keeps one 16-byte store a column.
- **`constexpr bool VT = HG <= 2`.** HG 4's static LDS is 54784 B and the tile would put it past 64 KiB; it keeps
  `fragT`, which also gives the byte tests a free `fragT`-vs-tile comparison at heads 64. The tile is single-buffered, so
  a chunk that fills it waits at a third `__syncthreads()` before the stash (a second 16 KiB buffer does not fit).

## Why it lost

Three costs, all of them on the stash side, and the LDS budget gives no room to remove any of them:

1. **The store doubles, into a layout that conflicts.** The score side needs the chunk row-major (`keys`, read by 18
   `ds_read_b64` a wave) and the value side needs it column-major, so every piece is written twice: +1024 16-byte LDS
   stores a chunk. A column of the tile is 32 B (`16` u16), so the 64 lanes of a staging wave write 16 B every 32 B —
   four bank groups for 64 lanes, a 16-way conflict a dword phase. The reads save 48 instructions a fragment per wave but
   the writes cost roughly that many cycles again.
2. **The fetch moves onto half the threads.** The 8x8 transpose needs eight tokens in one thread, so at HG 2 (256
   threads) the latent fetch runs on 128 of them, eight pieces each, where it used to run on all 256 — half the
   warps in flight over the same latency, and one workgroup per CU at this LDS size leaves nothing to hide it behind.
3. **A third barrier a chunk, and it is not symmetric.** `vt` is single-buffered, so both head groups wait for the value
   product of the previous chunk before the next stash. `mla_attn_sel_sink` selects per row, so its two groups are
   unbalanced and pay more at that barrier — which fits its +61 % against the paged row's +22 %.

What would be needed is a conflict-free column layout (a padded pitch of 20 elements makes both sides optimal but needs
20480 B, and HG 2 would then be 67072 B of the 65536 B limit) *and* a double-buffered tile (another 16 KiB), i.e. a
kernel whose static LDS is smaller to begin with (K-41's single key buffer would free 18.7 KiB at HG 2 — enough for the
padded tile and a second buffer). HG 4 at 54784 B has the room but is the form prefill does not use at
TP2 (32 heads selects HG 2 whenever the row count reaches 64 workgroups), so a tile behind `HG == 4` would buy the
served prefill nothing.
