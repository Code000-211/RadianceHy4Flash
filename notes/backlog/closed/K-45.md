# K-45 (`moe_gather` wide kernel for f32 routing weights): CLOSED -- the audit row is stale on this model (K-19 fuses the gather) and at the served geometry the wave form is 107 us a layer slower

Item as written (backlog K-45): the wave-per-token gather's `wide_ok` admits only bf16 routing weights
(`libr4d/r4d_moe.hip:3533` at this HEAD; `:3476` at the audit's `c655f58c`); Hy4's `w.ew` is f32
(`hyv4flash_moe.h:126`), so "2048-row chunks run the 2-byte-a-lane `gather_kernel` plus two inverse-table
launches"; add `gather_wide_kernel<NW, F32>`; gain prefill +0.8 %, confidence high, effort S; verify with
`r4d_moe_gather_pin_form` form 1 against form 2 bytes.

## What was built and what it did

The wave form got an f32 body carrying the column form's law (`fmaf`, not the bf16 `acc + w*x`), the
launcher let f32 routing weights into it, and the emulator and selftest grew the shapes that pin the two
forms against each other. It is byte-identical to the column form at every shape (`measurements/K-45.md`
§5: 205 emulator cases, 0 failures, against 200 cases and 5 failures on the base library, all five the
f32 wave cases; `r4d_selftest --case moe_gather_bf16` 16384-row output byte-identical on both arms), and
it is **2.5x** where the item's shape is reachable at all -- 2048 tokens x top_k 8 = 16384 routed rows
x 1536, f32 weights, past the 512-slot self-scan bound: 143.7 / 152.5 / 152.3 us a launch the column form
against 57.3 / 68.3 / 57.3 us the wave form, and with the shared arm 143.3 / 142.8 / 155.5 us against
64.0 / 63.8 / 63.9 us (§1, three interleaved rounds, one card, the same kernel printed as the control).

## Why it does not merge: CARDS.md §2's second clause fails on the model the item names

- **Hy4-flash routes sixteen slots, not eight.** `arch/hyv4flash/hyv4flash.cpp:262` takes the block's
  `num_experts_per_tok`, and `arch/hyv4flash/hyv4flash_moe.h:443` (K-19) fuses the gather into
  `moe_gather_inv_i8g` exactly when `gather_q8_on()` holds, `s.latent % 256 == 0` and `top_k == 16`. So
  the served prefill gather is the fused **quantising** one at 1984 rows x 1536 columns
  x top_k 16, group 128, f32 weights -- not the plain `gather_kernel` the item's audit row was taken on.
- **At that geometry the wave form is slower, not faster.** In one library, one run, both forms pinned at
  1984 rows: 289.6 / 289.7 / 290.0 us the wave form against 182.1 / 182.2 / 182.3 us the sixteen-slot form
  for the fused op (315.6 against 203.2 us for the `moe_gather_inv` + `had_quant_act_i8g` pair), i.e.
  **+107 us a layer**, +4.4 ms on a 16384-token chunk over 41 layers (`measurements/K-45.md` §2). It is the
  shape and not the dtype: at sixteen slots a row the wave form's slot loop walks twice the codes.
- **So the only mergeable form bounds f32 to eight slots, a window Hy4 never enters.** With
  `kGatherWideF32Slots = 8` (the branch's bound) the served op keeps the kernel it had -- 182.4 / 182.4 /
  182.5 us against 182.4 / 182.4 / 182.3 us before -- and the plain path is no better:
  `RADIANCE_HY4_FUSE_GATHER_Q8=0` still routes sixteen slots, so the window does not open there either.
  The lane agrees: both arms' stamps hold **exactly the same 3772 rows of
  `r4d_moegather::gather_kernel16_q8<256,true>`** and no other `r4d_moegather` kernel, and no `moe_gather`
  row appears at all -- the lane never runs the shape this item speeds up (§4).
- **End to end is noise.** The TTFT pair (five pairs each way, run with the wide-everywhere intermediate
  `47d4c7f9`, so the strict case: pf6 1.999 .. 2.643 s against 2.030 .. 2.466 s, pf20 6.902 .. 8.329 s
  against 6.912 .. 8.244 s, §3) sits inside its own spread, and the commit that would merge cannot move the
  lane at all, since it runs the same kernel with the same bytes.
- **It also reached models nobody measured.** f32-routed blocks at top_k <= 8 past 512 slots would have
  switched to the wave form: `arch/glm5next/glm5next.cpp:268` (`mw.ew` f32 `{T, 8}`) certainly, and
  `arch/bailing_hybrid/bailing_hybrid.cpp:651` and `arch/flint/flint.cpp:283` depending on their top_k. The
  emulator says those bytes are identical, but no such model was served or stamped, and the issue asked for
  Hy4-flash.

The item's "otherwise" therefore applies: closed with these numbers and this reason, and the card's two
code commits (`47d4c7f9`, `d61d19c5`) are reverted here. `notes/backlog/measurements/K-45.md` stays as the
record of the raw lines those numbers come from.

## What a re-proposal would need (a new item, not a retry of this one)

- A wave form that beats 182 us a layer at **sixteen** slots -- the present one walks the codes twice
  (289.6 us), so it needs a slot loop that reads each code once, or a shape-specific unroll.
- Or evidence that Hy4's block stops taking K-19's fusion (`gather_q8_on()`, `latent % 256 == 0`,
  `top_k == 16`), which would put the plain f32 gather back on the served path at 32768 routed rows; the
  wave window would then still have to reach sixteen slots, because the eight-slot window does not catch it.
- Or a served model whose prefill gather is the plain f32 form at eight slots or fewer a row past 512 slots,
  with that model's own lane run.
