# X-03: rolling decode snapshot every N tokens — closed without code

Item as written (`notes/backlog/optimisation-backlog.md`): "Save into the sequence's running-turn slot when
the decode position crosses a multiple of 256 on the quantum (17.4 MiB d2h a rank, ~0.7 ms of link in the idle
direction). Gain agentic / code turns: next-turn re-prefill <= 255 + new tokens instead of reply + new (a
1K-token reply = 0.25-0.3 s of prefill today). Conf medium (the template must re-render the reply
token-identically, also with thinking on). Verify: `resume.py` with long replies; hashes."

**The measured answer, up front: the snapshot is written and indexed, and the next turn cannot reach it.** Two
independent reasons, both measured on the lane:

1. **A snapshot that passes its own correctness check is written about once per 1,000 reply tokens, not every
   256.** The design indexes a snapshot only when the row committed at exactly the position it was planned at,
   i.e. every draft that row verified was taken. In a 1,024-token reply the build reserved 17 slots on the
   grid; 16 rows were cut short (committed at a position other than the planned one — the store refuses and
   returns the slot), and one committed, at 7,712, 85 tokens into the reply. Seventeen rows of a 1,024-token
   reply landed on the grid and one of them passed its own check, so the bound the card claims (a resumable
   position at most 255 tokens behind the reply's end) cannot hold as built: a usable snapshot appears about
   once per 1,000 reply tokens, at a position the reply does not choose.
2. **No position inside a reply is reachable by the next turn at all.** The prefix cache is content-addressed
   over the prompt's token ids, and the assistant turn does not re-render token-identically: the reply's 16th
   token (index 15, absolute 7,642) is **13** as generated and **364** when the same reply text is re-encoded
   through the chat template, so the block chain departs 13 tokens into the reply (7,640) and any snapshot
   keyed after it — the 7,712 one included — can never be matched. This is the item's own "Conf medium"
   caveat, and it is structural: the engine has no chat path that replays generated token ids.

Turn-2 prefill is therefore identical with the flag off and on — **1,108 / 1,098 / 1,096 tokens, all 12
arm-runs (6 conversations a side)**, and the replies are byte-identical — so the change gains nothing and costs
nothing measurable.

## What was built, and where it stays

The implementation is preserved on `krisf/RadianceHy4Flash:x03-impl` (tip `3f51b541`), no PR:

- `4dbac561 feat(sched): rolling decode snapshot every N tokens` — the card's mechanism as designed:
  `reserve_checkpoint_slot()` / `commit_checkpoint_at()` in `core/mem/prefix.{h,cpp}` over a factored
  `take_ckpt_slot()`, the `RAD_E_UNSUPPORTED` virtuals and `prefix_hash(r,pos)` in `core/sched/mem_iface.h`,
  `SchedReq::last_dsnap` / `reserve_ckpt_deferred()` / `dsnap_candidate()` / `commit_dsnap()` in
  `core/sched/scheduler.{h,cpp}`, the `decode_snapshot` grid and its startup line in `core/sched/geometry.*`,
  `--decode-checkpoint-interval` (default 256) in `core/config.cpp` and `core/rad_core.h`, three `sched_test`
  cases, one `mem_test` case and the `FakePC`/`scripted_steps()` fixtures.
- `2b3d22ec test(config): list --decode-checkpoint-interval among the options that parse`.
- `3f51b541 fix(sched): take the decode snapshot on the row issued ahead too` — found here: the hook sat only
  in `step()`'s decode branch, which plans a row only when the ahead step was refused, so with the engine
  issuing ahead every step **no decode snapshot was ever reserved** in a 1,024-token reply (0 candidates).
  `step_next_locked()` builds those rows and now carries the same deferred reservation. With it the reply
  writes 12-17 candidates and `radiance:linear_checkpoints_written_total` moves 4 -> 16-21.

The store's contract held where it was exercised: the one row that committed at exactly its planned position
was accepted and indexed, so "an all-accepted spec row leaves the linear state of its last position" is
consistent with that observation. It was never resumed into, so the saved state's content is **untested** —
the byte-identical replies below prove the flag is inert, not that the snapshot is right.

## Why the lookup cannot reach a snapshot (the store, read directly)

Instrumented build of the same `3f51b541` (log lines only, no logic change), one `longresume` run:

- Turn 1 reserved 17 snapshot slots inside the reply (7,645 onward). `commit_checkpoint_at` answered
  `RAD_E_STATE` for 16 of them — the row committed at a position other than the planned one, the documented
  "drafts cut short" path — and `RAD_OK` once, at **7,712**.
- At turn 2 the checkpoint index held `[1984 3968 5952 7616 7712]`: the 7,712 snapshot was **still there**
  (it is the session's tip, and retention keeps it), so LRU/retention is not the blocker; neither is the key
  or the session identity — the same prefix cache, chain and session are used on both sides.
- The block walk matched **1,910 blocks = 7,640 tokens** and then found no entry for block 1,910. The block it
  wanted at 7,640..7,643 was `[2531 12375 364 494]`; turn 1's generated reply had
  `[2531 12375 13 ...]` at its own indices 13..15. The reply's 16th token re-encodes as 364, not 13, so from
  absolute 7,642 the two chains differ and every snapshot inside the reply is unreachable.

Consequence: the deepest resumable checkpoint is the prompt's prefill checkpoint at 7,616, which is what both
arms resume from — 8,724 - 7,616 = 1,108 tokens.

## What ran, and what did not

**Ran**: 2 replicates x 2 arms x (3 resume conversations + c1 + c8 + 4 greedy texts); the instrumented
diagnostic run above; the test set with the cards free. **Did not run**: the thinking-on path the item also
names; a token-id replay path (`/v1/completions` with `prompt` as an int array) — no agentic client uses one,
and the chat API does not return token ids; a from-clean rebuild of all 506 targets by this worker; any other
model or lane.

## If it comes back

Reopen when both of these hold, and re-run this exact A/B:

1. **A reachable chain**: the served path can present the reply's generated token ids (per-message token ids,
   or a client that replays `prompt` as an int array), so the next turn's chain is the generated chain rather
   than a re-encoding. Check it first by comparing the reply's ids with the re-encoded ids at the same
   positions — today they differ 15 tokens into the reply.
2. **A snapshot rate that meets the bound**: the all-accepted-row rule yields ~1 snapshot per 1,000 tokens.
   Either the documented `n_spec == 0` fallback (index only rows with no drafts, which end exactly on the
   grid — it forces the one-token boundary row this design set out to avoid) or an explicit re-verify of a cut
   row's state.

The bar stays the item's: turn-2 prefill of about the new tokens (64 plus the template's ~20) instead of
1,108, byte-identical replies, and the flag inside noise at c1/c8.
