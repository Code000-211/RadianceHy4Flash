# K-56b `attn_kv_sink_h256`: a 64-row query tile (`bq` axis) at window 512

State: built and measured on one lane; the change sits in the commits on the branch
(`libr4d/r4d_attn_kv_sink_h256.hip`, `libr4d/r4d_rows.cpp`, the emu and selftest cases, `docs/OPS.md`). The merge bar's
remaining rows (stamps on a served chunk, `rad-tune` picking the axis, the e2e greedy text) are listed at the end, and
none of them can be produced from a kernel lane.

## The item

A workgroup of `bq` query rows reads keys from its first row's window start to its last row's own key: `window + bq - 1`
keys, of which each of its rows sees `window`. At window 512 with 128 rows that is 639 keys and 20 % of the key tiles
masked; with 64 rows (8 waves, 256 threads) 575 and 11 %. `bq` {128, 64}, default 128, `RG` a template parameter
(`kThreads = bq * 4`), expected −8..−10 % at window 512 and nothing where the mask is the same for every row. The item
puts the gain inside the prefill bound (perf.md §1, E4) because the narrower workgroup moves a row's key tile grid.

## What the change is

- `libr4d/r4d_attn_kv_sink_h256.hip`: the tile became a template (`Tile<BQ>`: 8 or 16 waves, `BQ*4` threads, `RG =
  BQ/16`, `NKI/(BQ*4)` keys a thread) and the kernel one over it; the launch reads `bq` off the tuned axis and refuses
  anything but 64 or 128 with `RAD_E_SHAPE`.
- `libr4d/r4d_rows.cpp`: `tAttnKvSink` — the row's only `RadTunable` axis, `{64, 128}`, default 128, on the prefill row
  `attn_kv_sink_h256` (`NOTUNE` → `ROW(tAttnKvSink)`).
- `tests/r4d_emu/test_attn_kv_sink.cpp`: the same geometries at `bq` 64, each against the f64 port of libref inside the
  op's bound (2e-3 + 8e-3·|w| an element, 5e-3 of a row's L2) and the two points against each other inside twice that,
  since they are not byte-equal by design; plus `bq` 96 refused.
- `libr4d/r4d_selftest.cpp`: the `attn_kv_sink_h256` case gains five `bq 64` geometries at Hy4-flash's shapes, and a
  `--perfkvsink [iters] [rev]` mode that times both points at the prefill geometry in one process, each launch alone.
- `docs/OPS.md`: the axis is described as the kernel's, not as a parameter of the op (see "Decisions").

## Measured on one lane

Lane: `iks`, one R9700 `gfx1201` (32 GB), through `gpu1`; the eight cards' `power1_cap` read back at 210 W before the
runs; built with `-DRAD_WITH_HIP=ON -DRAD_GPU_TARGETS=gfx1201` (RelWithDebInfo) on iks' own toolchain
(`moebius-gpu/configure.sh`). *Base* is the branch's tree with `libr4d/r4d_attn_kv_sink_h256.hip` and
`libr4d/r4d_rows.cpp` taken from `0d2e5102` (the merge before the change: `RG = 128` fixed, no axis), i.e. the same
harness and build options with only the kernel reverted.

```
# after (branch tree)
gpu1 ./build/bin/r4d_selftest build/radiance_home/kernels/libr4d.so --perfkvsink 20
gpu1 ./build/bin/r4d_selftest build/radiance_home/kernels/libr4d.so --perfkvsink 20 rev
# base (0d2e5102's kernel and rows), same two commands
```

`--perfkvsink` reports the median of 20 warm launches with a 256-launch L2 flush between them, and runs the two `bq`
points in both orders so a thermal or clock drift shows up as a disagreement between them. Us a launch, the two orders
averaged; "base" is the pre-change kernel, "after 128" the branch at its default, "after 64" the axis at 64.

| shape (one sequence, M rows after the prefix) | base | after 128 | after 64 | 64 vs base |
|---|---|---|---|---|
| sliding TP1, 64 heads, M 1024, prefix 511, window 512 | 798.5 | 806.0 | **759.5** | −4.9 % |
| sliding TP1, 64 heads, M 1024, prefix 0, window 512 | 624.5 | 626.0 | **574.5** | −8.0 % |
| sliding TP1, 64 heads, M 512, prefix 0, window 512 | 249.5 | 247.0 | **228.5** | −8.4 % |
| sliding TP1, 64 heads, M 2048, prefix 0, window 512 | 1398.0 | 1397.0 | **1336.0** | −4.4 % |
| sliding TP2, 32 heads, M 1024, prefix 511, window 512 | 405.0 | 404.0 | **386.5** | −4.6 % |
| sliding TP2, 32 heads, M 1024, prefix 0, window 512 | 337.0 | 329.5 | **307.5** | −8.8 % |
| sparse TP1, 32 heads, M 2048, window 0 | 1348.0 | 1352.0 | 1394.0 | +3.4 % |
| sparse TP1, 32 heads, M 1024, prefix 1024, window 0 | 984.5 | 996.0 | 1037.0 | +5.3 % |
| sparse TP1, 32 heads, M 512, window 0 | 149.5 | 146.5 | 135.0 | −9.7 % (noise, see below) |
| sparse TP2, 16 heads, M 2048, window 0 | 734.0 | 735.0 | 754.0 | +2.7 % |

What the numbers say:

- At window 512 the 64-row tile is faster at every shape the item names, by 4.4-8.8 % (8.0 % and 8.8 % at M 1024,
  4.4-4.9 % at M 2048 and at the cached-prefix case). The item expected −8..−10 % at M 1024 and −1.7 ms per 1024
  tokens at TP1; M 1024 lands on the low end of the expectation, the longer sequence and the prefix case below it.
  The mechanism is the one the item states: the masked share of the key tiles falls from 20 % to 11 %.
- **The 128-row path is unchanged**: base against "after 128" is −2.2..+1.2 % over all ten shapes, i.e. inside the
  run-to-run spread of the two orders (up to 2 % on the prefix case), so the template did not cost the default
  anything and the axis is the only difference.
- Where the mask is the same for every row (window 0, the dense layers) 64 rows is 2.7-5.3 % slower: more workgroups,
  the same work. That is why the default stays 128 and the axis is the tuner's.
- The one sparse point that looks faster (M 512, window 0) is not a real gain: the two orders disagree by 9 %
  (0.141/0.129 against 0.151/0.142) on a 135-150 us launch, and the same shape at M 2048 is slower at 64. Left as
  measured; no conclusion is drawn from it.

Static, off the lane: `libr4d/isa/res.sh` on this build gives 168 VGPR / 37192 B LDS / 9 waves a SIMD modelled for the
128-row instantiation and 176 VGPR / 28968 B LDS / 8 waves for the 64-row one, no spills and no scratch in either. The
LDS per workgroup falls (37 KiB → 28 KiB) because 512 threads' staging becomes 256's; VGPR rises by 8 and stays under
the 256 cap, so both forms keep their waves resident.

## Decided without being able to ask

- **The doc row loses `bq`.** The issue asks for a tuned axis, not for a new op interface; `RadTunable` values reach
  the kernel as parameters the *core* appends after the caller's, so `bq` is not something a plugin declares. Listing
  it in the parameter column made the table wrong (and a caller who followed it was refused by `Registry::validate`),
  so `docs/OPS.md` now says it is the kernel's axis, as the file already did for `stable` and `mb`.
- **Default 128.** The item says 128 "until measured"; now it is measured: faster at window 512, slower where the mask
  does not shrink, so 128 stays the default and `rad-tune` picks per shape.
- **The kernel row is `--perfkvsink`, not `rad-kbench`.** The checked-in fixtures carry no `attn_kv_sink` case
  (`data/kbench_rows/*` and `data/kernels.rkb` have none), so a kbench row for it needs the 138 GB container; the
  selftest's perf mode times the same geometries the item names in one process, both orders, which is a stronger pair
  than two kbench runs. `CARDS.md` §1 lists the perf modes as the kernel lane's tools.
- **The note lives here** rather than beside the item in `optimisation-backlog.md`: that file's entries are written
  when an item is closed, and the close is the owner's.

## Seen and left alone

- `tools/ops_doc_check.sh:41` has an apostrophe in *Debian's* and another in *Ubuntu's* inside the single-quoted `awk`
  program, so the shell cuts the program there: the check runs a truncated `awk`, prints nothing and exits 0 for every
  table on every tree. A copy patched to drop the two apostrophes reports 10 pre-existing disagreements on `HEAD`
  (`mla_attn_paged_sink` `row0` among them) and none for `attn_kv_sink`, which is how this change's doc row was
  checked. The one-line fix is not in this change: it changes what every row on the tree is checked against, and the
  ten rows it would then report are someone else's drift.
- `mla_attn_paged_sink` `row0` is the same doc-vs-schema drift this change fixes for `attn_kv_sink`
  (`docs/OPS.md:3768` has it, neither schema declares it).
- `tests/museglimmer_test.cpp` does not compile with the ROCm clang 24 this worktree builds with (`-Wc++11-narrowing`
  at :200, :453, :466-467), so `cmake --build build` without a target list stops there. Nothing in this change touches
  it; the targets this change needs build and pass.
- `libr4d/r4d_rows.cpp` compiles with 18 `-Wunused-const-variable` warnings (the `c*` constraint arrays and `o*`/`p*`
  operand specs of fp8/MX rows — `cMoeGemmQ`, `cGemmNtQGatedMx`, `cFp8F32Scale` and their kin). They are not from this
  change: compiling the file with the project's own flags at `0d2e5102`, at `7eb160fa` and at this head gives the same
  18 names byte for byte, and none of them is `attn_kv_sink`'s. The tree builds with `-Wall -Wextra` and no `-Werror`,
  and the declarations belong to rows other than this item's, so they stay; the change adds no warning to any of the
  three translation units it touches (diffed the same way).
- `rad-kbench`, `stamps` on a served chunk and `rad-tune` were not run: the first two need the model container and the
  last a tuned run of it, which a kernel lane does not have. For the merge bar that leaves: a stamps row for
  `attn_kv_sink` on the first non-absorbed chunk (basis 42 x 764 us = 32 ms, so −1.4..−2.8 ms at −4.4..−8.8 %), a
  `rad-tune` report showing which window picks 64, and the greedy text on u3 with a > 2K prompt (logprob drift
  reported) that the item's Verify asks for.
