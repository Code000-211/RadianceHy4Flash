# M-05 (heat `min_gain` 3 at high residency): CLOSED — promotions fall 25-60 %, but the decode rate is 1.0-1.3 % lower at c1 and c8 on iks-A, and the lane's served shape never crosses the 75 % bar

Item as written (backlog M-05): residency-dependent default for `HeatParams::min_gain` (`core/place/heat.h`): 1.5 below 75 %
resident, 3 above; "tok/s within noise, promotions -40..-70 %, link h2d -55 %". Verify: `work/churn/churn.py` A/B three runs,
greedy identity.

PR #250 (Gats-codeserk, code commit `15d4e1f`) built it: `HeatParams::resident_min_gain()`, `min_gain_adapts` opt-in set by
the served engine only, `RADIANCE_HEAT_MIN_GAIN` wins, a startup line saying which value and why, and a test
(`heat_min_gain_follows_residency`, passes under ctest here). The code is correct and tested. It is not merged, because the
merge bar (CARDS.md §2.3, "tok/s not worse beyond noise") does not hold in our own measurement.

## Measurement (lane `iks-A`, 2 x R9700 at 210 W read back before each run, u3 container, `nospec.yaml` with `max-model-len: 8192`, 85 % of movable bytes resident, so the rule fires)

untouched, so this is the base's behaviour). After = the default (startup line: `min-gain 3.00 (min-gain from 85 % of the
movable bytes ...)`). Binary: PR head `15d4e1f` merged with base `6e76ed7`. Three interleaved runs per arm
(`scripts/backlog/m05-ab.sh`, config `scripts/backlog/nospec8k.yaml`; tag `m05-new-N` / `m05-old-N`), one server per run,

- Promotions: -60 % at c1, -25..-35 % at c8; h2d -61 % at c1, -20..-30 % at c8. The direction is the audit's; the size is
  smaller at c8 than the -40 % the PR measured on the local lane.
- Decode rate: **-1.0 % at c1** (the arms do not overlap: 73.71-73.95 against 74.59-74.64) and **-1.3 % at c8** (means 316.2
  against 320.5). The PR author measured the same sign at c1 on the local lane (-0.8 %, arms not overlapping) and c8 inside
  noise there. The resident hit share is lower (0.974 against 0.983 at c1): the guard refuses promotions that would have
  paid.
- Output parity was not re-run here (the code decides which units move, not what is computed); the PR reports byte-identical
  greedy text in 15 runs on its lane.
- The lane's served shape (`max-model-len: 65536`) keeps 61 % resident, below the bar, so the shipped configs run `1.5` with or
  without the change: the change would only fire on a shorter context than the lane serves.

## Why closed

§2 needs the targeted quantity faster and tok/s not worse beyond noise. The targeted quantity (promotions, link traffic) is
lower, but nothing the user sees improves: the two machines agree that the decode rate goes down by about 1 % at c1, c8 is
-1.3 % here, and the configuration it applies to is not the served one. The backlog's own expectation ("tok/s within noise")
was met at c8 on one lane and not on a second one. If a later item (M-06 paced copies, M-07 link gate) makes the copies the
bottleneck at c8, `RADIANCE_HEAT_MIN_GAIN=3` is still available per run and the PR's `resident_min_gain` is the place to
reopen from (PR #250, `15d4e1f`).

Thank you to Gats-codeserk for the implementation, the test, and for stating the c1 cost and the served-shape finding in the
PR before anyone asked; both turned out to be the deciding facts.
