# D-11 — Link-aware verify price: closed, no measured gain

**Number and reason.** The load-aware rule's verify row is now priced with the link the last steps
paid per routed row, measured on one lane as `coupled03.yaml` c4/c8 pairs: the change is exact
(byte-identical greedy output, four prompts, every run) but it moves no decision the served step
makes — `tok/step` at c8 is unchanged (21.33–22.76 either side) and the c8 throughput delta is
+16.1 %, +33.7 %, +6.3 % and +0.3 % over four pairs, where the pair whose expert-cache state
matched on both sides says +0.3 %. The spread of identical code on this host is larger than any of
it (the before side alone ran 242.15 … 365.15 tok/s at c8), and the c4 column — where the item
expects *nothing* — moves as much as c8 (+23.7 %, +49.7 %, +2.9 %, −3.1 %), so the deltas follow the
run's cache and host state, not the lever. So the change is reverted and the item closes: the
link is not what the rule's decisions are made of at `draft-depth-stop 0.3`, and pricing it changes
no row the rule drafts.

The implementation and its tests are in `81ea7984` (the rule and the engine's feed) and
`651f07f5` (the feed read from `stream_bytes`, the item's own basis) on this run's branch if a
future card wants the lever for a different stop threshold or a rule that varies its row count — the
design is described below so that it does not have to be found again.

## What was implemented (and measured)

- `core/sched/draft_depth.h`: `DraftDepthCfg::load_link_ms[kLoadSeqs + 1]` — the link a routed row
  pays, by drafting rows `n`; `draft_depth_load_cost` adds `load_link_ms[n] * R` to the row price;
  `draft_depth_routed_rows(R, n, D) = R + n * D` — the rows a step routes experts for (its verify's
  rows and its drafter's `D` passes of the `n` drafting rows);
  `DraftDepthOnline::Link {ms, n} link[kN + 1]` and `draft_depth_online_step(..., double link_us,
  int routed)` feeds it: `link_row = link_us / 1000 / routed`, an EMA with a half-life of 64 steps,
  published into `load_link_ms[n] = clamp(K.ms, 0, 5)` once 32 steps have been seen.
- The fit is on `fit_ms = ms - link_row * R` (clamped at 0.25 · ms): the verify rows' link is taken
  out of the row coefficient and added back by `draft_depth_load_cost`, while the drafter's own
  passes' link stays in `load_round_ms[n]` (a round routes `n` rows as well), so the link enters the
  cost once and is not counted twice.
- `core/engine_draft.cpp` / `core/engine.h`: per pure decode step, rank 0's `HeatStats::stream_bytes`
  delta over `link_bw_gbs` (27.6 GB/s, `notes/backlog/refs/kernels/experts-streaming.md`: a missed
  expert is 1.82 MB a rank, which is 66 µs at that rate) and the step's routed rows. No new flag:
  the fields default to no link, and the lane's existing `draft-depth-load: on` with the default
  online calibration carries the feed, so before and after run the same config.
- `tests/mtp_rrs_test.cpp`: `load_aware_row_price_carries_the_link_the_steps_paid` (cost and the
  tile decision), `online_calibration_prices_a_row_at_its_trunk_time_and_the_link_the_steps_paid`
  (a differential: 8000 steps with the link fed against the same steps with it held — the row price
  equal both sides, the link exactly `link_us / routed` per row, the round price rising with the
  drafter's own passes, the marginal row carrying row + link), and a link-fed case in
  `online_calibration_keeps_the_target_law…`. All 14 `mtp_rrs` shards passed with the change in.

## Why it does not pay

- **The link is a small share of the row.** At c8 the steps paid 110–320 missed expert units
  (the backlog's own figure is 111), i.e. 7.3–21 ms of link across the step's ~91 routed rows,
  which is **0.08–0.23 ms a row** against a calibrated row of 0.62–0.83 ms — a 12–27 % raise.
  With `draft-depth-stop: 0.3` the rule almost never sits on that margin: the rows it drafts, the
  rounds it runs and the tokens a step makes do not move (`tok/step` 21.33–22.76 either side,
  `routed/step` within 4 % across all runs), so nothing becomes cheaper.
- **The item's premise does not hold for this rule.** D-11 assumes the verify row is under-priced
  for the steps that stream experts; measured, the round price already carries the link for all the
  rows a round routes, and the row price is fitted on step times that include it on average. Adding
  a per-row link term on top shifts the price by a sixth of a row and changes no decision — the
  served effect is the run-to-run spread of this host, not the lever.
- **Where the deltas come from.** The after side of pairs 1, 3 and 4 also had a higher expert-cache
  hit rate (0.9844–0.9868 against 0.9620–0.9833) and fewer missed units a step; pair 5, where both
  sides hit alike (0.9864 / 0.9866) and the cache state matched, is the only one that measures the
  lever alone, and it says +0.3 % at c8. The c4 column (the item expects nothing there) moving as
  much as c8 is the same statement from the other side.

## What would have to change for the lever to pay

The link would have to change *which* rows are verified, not just their price: a rule that varies
its row count with the link (draft fewer rows on the steps that stream experts, more when the hot
set is resident), or a stop threshold low enough that the 12–27 % raise moves the decision. Both are
a different item. What is *not* the problem is the measurement: with pairs run alternately and the
cache state matched (pair 5), 0.3 % is what the lever does.
