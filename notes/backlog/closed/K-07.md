# K-07 (`moe_iqr` / `moe_down_dec` one descriptor load per block): CLOSED — the run search is not on the critical path, and a block that takes several column tiles costs warps

Item as written (backlog K-07, `notes/backlog/optimisation-backlog.md`): "`r4d_moe_iqr.hip:278-318` (wave 0: 17 `off[]`
loads a lane, scan, `lds_barrier`), `:333-334` (`C.w[e >> cshift]` dependent pointer load), then `D::fetch`. At M = 1 the
grid is 16 runs x 96 y-blocks of 128 threads and every block repeats the head. Either (a) let a KW 4 block take 2-4 tiles
in turn (lift `static_assert(TPW == 1u || KW == 1u)`), or (b) have `router_sigmoid_topk_scatter` write a run descriptor
list (expert, rs, re, W ptr, S ptr) so a block does one load. `moe_down_dec` has the same head." Why: routed gate_up
43.4 us mean (33.5 warm) for 14.8 MB (floor 26 us), routed down 26.9 (19.8) for 9.7 MB (floor 17): "~17 us a layer above
the byte floor at one row = 0.7 ms a pass; est. a third of it recoverable". BI, effort M.

This branch built option (a), measured it on one lane and with `--perfmoeiqr`, and reverts it: nothing got faster, and
where the block count is what limits the launch it got slower.

## What the code says (at HEAD, after this branch's revert)

- The head is one wave's prologue, paid once a block and not once a tile: `r4d_moe_iqr.hip:283-312` has wave 0 load its
  17 clamped expert offsets (`kMaxExpert` 512 / 32 lanes + 1), mask them to the tile's 16 rows, inclusive-scan the mask
  and let the lane holding run `jrun` search its own mask by halves into `s_sel[0..2]`; then one `lds_barrier()`
  (`:331`) hands it to the block, and `C.w[e >> cshift]` / `C.s[...]` (`:334-335`) are the two dependent pointer loads.
  The other `NW - 1` waves of the block wait at that barrier and then work: 17 loads and a 32-lane scan a block is a
  few hundred nanoseconds of one wave's time, which the block's other waves and the card's other blocks overlap.
- The decode grid at M = 1: `wide_k` (`:767`: `nkb >= 8` and `T < kOneWaveMinRows` (20, `:720`) or `(N/16) % 4`) sends a
  wide-K decode to `R4D_MOEIQR_GO(4u, 1u, false, 1u, 1u)` (`:781`): four waves a block, 16 columns a tile, one tile a
  block, `kCols = RTB * TPW * 16`. Hy4-flash at TP2 (T = 16, gate_up 16 x 1536 x 1536) then launches 16 x 96 = 1536
  blocks of 128 threads, three K-tiles a block.
- `moe_down_dec` has the same head (`r4d_moe.hip:1595-1654`) but already takes several column tiles a block: G comes
  from `kMoeDownDecG2Rows` 200 / `kMoeDownDecG4Rows` 480 / `kMoeDownDecMaxG` 16 (`:1541-1542`), and the rule's own
  measurements are in the comment above it — at ten rows G 1 -> 4 was *worse* (too few waves), so under 200 rows it
  runs G = 1. At M = 1 the down launch is 17 x 24 = 408 blocks: a quarter of gate_up's, so a quarter of the head.

## What was built and measured, then reverted

Option (a) of the item, in `libr4d/r4d_moe_iqr.hip` (the code is not kept):

- `static_assert(TPW == 1u || KW == 1u)` relaxed to `TPW == 1u || KW == 1u || RTB == 1u`: a wide-K decode block takes
  `kWideTiles` column tiles in turn (`for tp in 0..TPW-1`, each tile 16 columns, all of K).
- The fold and the store of the tile's partials, which HEAD lets the owning wave do with `if (kph != 0u) return`
  (`:413`, `:507`), became a guard, so a block that folds several tiles keeps the same per-tile fold order
  (`w = 0..KW-1`, `red(w)` in its own wave's LDS tile), the same store condition and the same `s_tr` (8704 B) — and
  one extra `__syncthreads()` a tile, only when `KW > 1 && TPW > 1`, so tile n+1's scatter cannot land on tile n's
  partials. Arithmetic, LDS and stores are unchanged: the change is BI by construction, which the checks below confirm.
- A `wide_k_tiles` rule (2, halved to 1 where `N % (16 t)` does not divide) and `r4d_moe_iqr_pin_wtiles` beside
  `r4d_moe_iqr_pin_map_tiles` (`:982`) so one build could time 1, 2 and 4 tiles a block.

**Correctness.** `r4d_selftest --case moe_gemm_iqr` (one card, `iks`) with a new check in `moe_iqr_case`: every case in
the wide-K decode band re-launches at pins 1, 2 and 4 and `memcmp`s the whole of Y against the rule's result — the
tolerance is *none*, byte for byte, which is what BI asks of this item. The seven decode-band cases it reaches (B =
2/3/5/6 at T = 8, 256:256 x 1280:1280, E = 32; B = 4 at T = 12, 768:512 x 2560:2560, E = 64, and its dropped-slot
variant) all pass at every pin, and each arm is also compared to the dense `gemm_iqr_nt_m64` reference at the case's
existing bound `|a - b| <= ldexp(|b|,-7) + ldexp(rms,-8)` (7 bits of bf16 mantissa plus 8 of the row's rms: the sum of
K bf16 products in fp32, where a bf16 output rounds at 2^-8 relative). The whole row's case set is 80 checks, 0
failures. `--perfmoeiqr` printed the same fnv-1a of Y in every arm of every shape and both builds (e.g.
`0d236a4cbc64a70b` at 16 rows, B = 3), so the kernel-level numbers below compare identical outputs.

**The RDNA4 ISA suite** (`bash .radisa/check-tree.sh --compile-commands build/compile_commands.json --changed-since
claude/peaceful-wright-hhqnhi --jobs 16`) was clean on the change: 1 file, 74 kernels, PASS, 0 errors, with four
`REGISTER_SPILL` warnings (1-4 VGPR) on the `FormT<6, 4..6, ...>` instantiations the change adds — the code is reverted,
so neither the errors nor those spills are in the tree.

## Why it closes without code

- **The merge bar is not met.** §2 asks for the targeted kernel or op measurably faster in ms. The stamps move by noise
  and in the wrong direction for a win that would clear it: `moe_iqr` 46.6 -> 46.4 us a launch (−0.4 %), routed gate_up
  1909 -> 1903 us a pass (−0.3 %), c1 +0.4 % tok/s; and where the change does bite on the kernel it costs 1-15 %
  (`--perfmoeiqr`), end to end that is invisible only because the grid there is big.
- **The head is not the 17 us.** The measurement's own refutation: deleting half the searches (a quarter, at four tiles)
  removed no time at the Hy4 grid and lost time at the smaller one. A prologue that is free when deleted cannot be a
  third of the excess. The audit's K-2 estimate ("est. a third of it recoverable") is about the whole gap to the byte
  floor; this experiment puts the run search at ~0 of it, which also argues against option (b): a descriptor list would
  shorten the same wave-0 prologue and the same barrier.
- **Where the gap sits.** The 16-row gate_up launch streams its codes at 471-750 GB/s (table above) and its time does not
  follow the block count's head; it follows the tile's own work — 16 columns a wave, the LDS transpose and its barriers,
  the trellis decode's instruction count. A later card would measure the wave's column count and the transpose before
  touching the prologue again.
- **`moe_down_dec` was left alone** for both reasons: its head is a quarter of gate_up's (408 blocks at M = 1), G > 1
  below 200 rows is the "too few waves" case the code's own numbers reject, and the only lever left there is option (b),
  whose ceiling this card measures as ~0. It also already does what option (a) asks (a block takes G column tiles),
  which is why the item's down half reads as done before it starts.
