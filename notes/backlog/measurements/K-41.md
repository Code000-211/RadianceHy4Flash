## Clause 1: output byte-identical

    head  r1,r2,r4,r5,r6: d6da4fb3 0699709c e7a23c5d 466e53a2  (kb 1 pinned)

Identical in all thirteen completed served runs. The default (`kb` 2) is the same code the base has: the object file
`build/libr4d/CMakeFiles/libr4d.dir/r4d_mla_sink.hip.o` hashes `8e99f506bf45c4…` both before and after the rename that made
the second buffer an index expression, so the default arm ships unchanged machine code.

Kernel level: `tests/r4d_emu/test_mla_sink.cpp` runs every declared form of both sink rows at `kb` 1 and `kb` 2 and compares
the two byte for byte (265 checks, 0 failures, `--filter mla_sink`); `kb` 3 (or any value but 1 and 2) is refused with
`RAD_E_SHAPE`. On a card, `r4d_selftest` reports 60 ok / 0 fail, 21 of them "kb 1 == kb 2" or "kb 1 == rule" over the
paged, the selected and the chained forms.

The chained instance (a decode launch takes it, so it was among those running when a run stopped; the selftest does not
reach it because it passes no chain) was checked against the reference oracle with `rad-kbench --chain-forms`:
`--op mla_attn_paged_sink --max-cases 1 --max-tok 512 --chain-forms --bench`, once with the axis pinned to 2 and once to 1:
**168 checked, 168 passed, 0 failed, 0 diverged, worst rel_l2 4.422e-04 on both arms** — the same numbers, so the two key
buffers agree on the chained form as well.

## Clause 2: the sink is faster

### Per launch, `rad-tune` (both candidates of one row, one process, same warm-up)

`rad-tune --op mla_attn_paged_sink --max-tok M`, three runs each with a fresh tune directory, µs a launch:

| point | kb 2 (default) | kb 1 | gain |
|---|---|---|---|
| heads=16 M=1024 (block 4, no window) | 849.5 / 849.9 / 850.4 | 642.6 / 642.6 / 642.9 | -24.4 % |
| heads=32 M=1024 (block 16, window 512) | 1043.2 / 1037.8 / 1042.4 | 767.4 / 767.4 / 771.2 | -26.0 % |
| heads=16 M=2048 | 3155 / 3141 / 3196 | 2515 / 2515 / 2513 | -20.2 % |
| heads=32 M=2048 | 2362 / 2346 / 2375 | 1859 / 1875 / 1856 | -21.0 % |

All four points pick `kb=1` (`build/radiance_home/tune/gfx1201-x2-AMD_Radeon_AI_PRO_R9700.tune`, 4 rows), and the tuner's
`vs default 0` on the chosen candidate says the choice is bit-identical at its 1e-3 tolerance. The selected row
(`mla_attn_sel_sink`, M=1024 heads=16) gains nothing: 3907.3 -> 3875.5 µs (-0.8 %), and its decode-height point keeps
`kb=2` (1246 vs 1250 µs) — that row is not LDS-limited, so the axis does not move it.

Median of the sink's `kb` 1 rows: M=2048 4 201 and 4 093 against 4 682 / 4 695 for base / head-default (two runs; the
pinned arm was run twice at 2048 and three times at 1024), so **-11.5 %** at the item's larger shape; M=1024 2 157 / 2 018 /
2 106 (**+3 %** on this mix). Where a chunk walks a long context the axis
wins 18-26 %; where a 512-key window makes a chunk cheap the third barrier costs 0-10 %, which is the reason the item asks
for an axis and not a switch: the tuner measures each point and keeps `kb` 1 only where it is faster. kbench's sink cases
are declared at 32 and 64 heads (its table); `rad-tune` above covers 16 and 32, the heights this model prefills with.
The default arm and the base differ by at most 3 % (the sink's machine code is identical in both) — the library holds 8
more instances for the second axis value, so code layout, not the kernel, moves those rows.

### Why: LDS and occupancy (read out of the compiled metadata by the RDNA4 ISA suite)

| shape | kb 2 | kb 1 | workgroups a WGP at kb 1 |
|---|---|---|---|
| HG 1 (16 heads, 128 threads) | 42 496 B (41.5 KiB) | 23 808 B (23.25 KiB) | 3 -> 5 (128 KiB LDS a WGP) |
| HG 2 (32 heads, 256 threads) | 46 592 B (45.5 KiB) | 27 904 B (27.25 KiB) | 2 -> 4 |
| HG 4 (>32 heads) | 54 784 B (53.5 KiB) | 36 096 B (35.25 KiB) | 2 -> 3 |

(The item's 41.6 -> 22.9 and 45.7 -> 27.0 KiB are the same buffers rounded; the compiled numbers above are exact.) The
register file allows 5 waves a SIMD in the fused HG 1 and HG 2 forms at both values, so LDS was the binding limit and the
occupancy gain is real. The item guessed +0.5-1.5 % prefill from that; the served prefill below gains 4.3-4.7 %, because the
sink is about a quarter of a prefill pass (audit F2.3) and the kernel gains 20-26 %.

## A run that stopped (reported, not explained)

`k41-kb1-r3` (sixth served run) stopped mid-`greedy`: `E model hy4-flash: stopping: the step loop failed with device error`.
The engine's own stuck-exit dump names device 0's compute queue with one packet in flight (`barrier-and done=1`, everything
else idle) and no queue advance for 5 s, i.e. a kernel that never retired or a queue the driver could not restore
(`amdgpu cwsr_enable=0` is the engine's own suggested cause). That run had no stamps, so the kernel is not named. It is
1 of 6 `kb` 1 runs and 0 of 8 `kb` 2 runs; it did not come back in the five `kb` 1 runs after it, and every completed
`kb` 1 run is byte-identical to the base. Checked so no divergence can deadlock the new barrier: `more` is block-uniform
whenever the trip count is (a workgroup covers one row and one split slot — `dim3(rows*splits, head groups)` — so all its
threads run the same number of chunks), the emulator passes with the barrier removed as well (parity only), and the card
selftest is clean at both values. The cause is therefore not established. The axis stays at 2 by default, so no served
configuration changes because of it; a machine that tunes `kb` to 1 should be watched for that stuck queue.
