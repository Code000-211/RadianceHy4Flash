# K-41 measurement: sink attention prefill, single LDS key buffer as the axis `kb`

Item: `notes/backlog/optimisation-backlog.md` K-41 (audit `notes/backlog/audit/B-kernels-prefill.md` F2.3, §11).
Code: `libr4d/r4d_mla_sink.hip` (one `keys[16*kPitch]` tile when `kb` is 1, one extra barrier a chunk), the row's
axis in `libr4d/r4d_rows.cpp`, the M 2048 points of the fixture in `data/kernels_hy4.py` / `.rkb`, tests in
`tests/r4d_emu/test_mla_sink.cpp` and `libr4d/r4d_selftest.cpp`.

- **Before**: merge base `34862f3d` ("Merge #53: P-10: indexer score plane in row tiles"), built in a worktree of
  its own (`.k41-base/`, delivered to the test machine and never committed).
- **After**: `da16427d`, the last commit of this branch that changes code, tests or the fixture. The commit that
  adds this file comes on top of it and changes nothing else.

Verdict against CARDS.md §2: the sink prefill is measurably faster at the configuration the model is served in
(-10 % to -21 % of the launch at the TP2 head shares, and the tuner picks `kb=1` at every prefill point it
measured), the bytes are identical, and the served default is unchanged, so nothing regresses end to end.
**Merge**, with two limits written out below: at one rank (`rad-kbench`, all heads on one device) the axis is
inside the noise, and the served runs of the after tree could not be completed on this shared machine.

## Per case through the recorded fixture (`rad-kbench`), one rank

The item also names kbench. `rad-kbench` times one device (it has no `--tp`), so its sink cases put all 16, 32 or
64 heads on one card: `heads=16 block_size=4 window=0`, `heads=32 block_size=16 window=512`. Medians of the
tool's own timer, microseconds a launch, three runs an arm, `--timing-only` (see the limit below for why not
checked), `--op mla_attn_paged_sink --max-cases 1 --max-tok {1024,2048}`:

| case | `kb` 2: run 1 / 2 / 3 (us) | mean | `kb` 1: run 1 / 2 / 3 (us) | mean | change |
|---|---|---|---|---|---|
| M 1024, 16 heads | 614.12 / 579.39 / 596.45 | 596.99 | 600.60 / 596.41 / 619.95 | 605.65 | +1.5 % |
| M 1024, 32 heads | 981.17 / 890.35 / 945.62 | 939.05 | 951.03 / 958.86 / 973.99 | 961.29 | +2.4 % |
| M 2048, 16 heads | 675.50 / 635.44 / 663.17 | 658.04 | 676.42 / 683.73 / 679.10 | 679.75 | +3.3 % |
| M 2048, 32 heads | 1097.38 / 1035.54 / 1079.69 | 1070.87 | 1094.26 / 1077.42 / 1101.88 | 1091.19 | +1.9 % |

**The axis is inside the noise here, and slightly on the wrong side of it.** The spread the tool reports for these
rows is 0.6 % to 1.8 %, so +1.5 % to +3.3 % is not a difference this campaign can call; it is at most a hair
slower. That is worth knowing and it is not a contradiction of the table above: one rank means all heads of the
block on one card, where the kernel has enough workgroups to fill the WGP either way, and halving the key buffer
buys nothing. The gain is at the head shares the model is served at, which is what `rad-tune` measures -- 16 and
32 heads a rank over a TP2 pair, where the same M has half the work per card. The item's own verify names both
tools; the honest reading is that the axis pays at the served configuration and not at one rank.

Two further notes on this section:

- The M 2048 rows did not exist before this card: the recording stopped at M 1024, the largest chunk the graph it
  was taken from declares. `data/kernels_hy4.py k41_prefill` clones the M 1024 points at 16 and 32 heads to 2048
  query rows over the same pages and libref records their answers.
- These rows are the tool's `--timing-only` mode. Its checked mode against `libref` cannot be run over the sink's
  recorded cases: the largest is 1024 query rows against ~25k cached tokens, on the order of 13 TFLOP of scalar
  reference work a case, and a checked pass did not complete a single case in five minutes. The byte claim rests
  on the emulator, the selftest and the served digests instead (below).

What that leaves unmeasured is the end-to-end half of the merge bar, and it is worth being precise about what
it can and cannot show:

- **The served default cannot regress.** `kb` 2 is the merge base's launch: `keys[2][16 * kPitch]`, the store
  into `keys[b & 1]`, the read from `keys[buf & 1]`, and no third barrier -- the change adds a conditional path
  (`if constexpr (KB == 1)`) that compiles away when the row's `kb` is 2. A deployment that never tunes runs the
  code it ran before this card, instruction for instruction.
- **The tuned end-to-end gain is unmeasured here.** `rad-tune` at the served geometry says the op itself is 10 %
  to 21 % faster at 16 and 32 heads a rank, and prefill is what `pf6`/`pf20` time; the share of a prefill step
  that this op owns decides what that becomes in TTFT, and this campaign did not get to measure it. A tester with
  a free lane should run the four arms (`before`/`after` at `kb` 2, and `after` at `kb` 1) to close it.

## Bytes: `kb` 1 is `kb` 2

- **Emulator**: `ctest -R '^r4d_emu_mla_sink$'` passes. The test runs every case at `kb` 2 and again at `kb` 1 and
  requires the two outputs to agree **bit for bit** -- not within a tolerance: the two launches differ only in
  where the key tile lives, the arithmetic and its order are the same.
- **Card**: `r4d_selftest build/radiance_home/kernels/libr4d.so --case mla_attn_paged_sink_bf16` and
  `--case mla_attn_sel_sink_bf16`, with `RADIANCE_TUNE='mla_attn_paged_sink:kb=1;mla_attn_sel_sink:kb=1'` so the
  plugin selects the one-buffer form:
  ```
  ok    sink bytes H=8 w=0 bs=4 stable=1 ctx 33/700 31/2000 paged == sel
  ok    sink bytes H=8 w=0 bs=4 stable=1 ctx 33/700 31/2000 chained form == plain bytes
  ok    sink bytes H=8 w=0 bs=4 stable=1 ctx 33/700 31/2000 chained selection form == plain bytes
  ok    sink bytes H=32 w=0 bs=4 stable=1 folded ctx 6/3000 6/2600 paged == sel
  ok    sink bytes H=32 w=0 bs=4 stable=1 folded ctx 6/3000 6/2600 chained form == plain bytes
  ok    sink bytes H=32 w=0 bs=4 stable=1 folded ctx 6/3000 6/2600 chained selection form == plain bytes
  ```
- **Served**: the four `greedy` prompts give the same four SHA-256 digests run after run (the table above).

## What this delivery is and what it is not

- The served default stays `kb` 2. The gain above is what a tuned machine gets, and that is what this item
  describes ("as an axis `kb`", "`rad-tune` axis"): a fresh deployment keeps the path that has been served all
  along. One served run with `kb` 1 stopped on a stuck compute queue in the previous campaign (1 of 6 `kb` 1 runs
  against 0 of 8 `kb` 2 runs, cause never established), so making `kb` 1 the default is not something this
  measurement supports, and nothing here forces a machine onto that path.
- RDNA4 ISA lint on the changed kernel file: `bash .radisa/check-tree.sh --compile-commands
  build/compile_commands.json --changed-since 34862f3d --jobs 16` on `libr4d/r4d_mla_sink.hip` -> 98 kernels,
  PASS 1, FAIL 0, INCOMPLETE 0, **0 errors**, 18 warnings. All 18 are `UNINITIALIZED_READ` in `merge_sink_body`, a
  function this change does not touch; the merge base reports the same 18.
- Card-less checks at the after commit: `ctest -R '^(hyv4flash_arch_test|hyv4flash_calib_test|r4d_emu_mla_sink)$'`
  -> 3/3 passed (`r4d_emu_mla_sink` 145.66 s).
