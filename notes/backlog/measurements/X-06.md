# X-06: the global suffix cache (FP-5) served, and DARTree's offline sizing (FP-6)

FP-5's code is already on the branch through X-04 (#232, merge `0c2f91db`): `33cbb805` (the global cache,
`--draft-suffix-global-mib`, default 256 MiB, 0 off) and `b1088f7a` (the suffix index built a prefill chunk at a
time, and taken over by the conversation's next turn). `X-04.md` measured only the prefix store, on `nospec.yaml`, so
no suffix chain ran there. This file adds the served A/B of the global cache, D-7's index cost at 64K, and FP-6:
whether DARTree for DFly2 (FP-9, L) is worth building.

- Tree: `0c2f91dbb629272d227808c4e4e61fb3d197de78` (Merge #232) for both arms. The global cache has a switch, so the A/B runs on one binary:
  ON = `draft-suffix-global-mib` at its default (256), OFF = `draft-suffix-global-mib: 0`. The take-over has no
  switch and is on in both arms.
- Machine: 4 x Radeon AI PRO R9700 (gfx1201), TP4, `power1_cap` read back 270 W on all four before every run, ROCm
  core 10.1 (`/opt/rocm/core-10.1`, its `clang++` as HIP compiler), 2026-11-25, measured by adamczhang.
- Container `hy4-flash-iqr-v4-u4.rad` (150444707840 B), `ngram-placement: ram`, `max-model-len: 65536`,
  `max-num-seqs: 8`, DFly2 with `num-speculative-tokens: 5`, `draft-coupling: on`, `draft-verify: traversal`,
  `draft-depth: adaptive` with load, `draft-suffix: on` (`draft-suffix-max` is clamped to the 5-row block),
  `busy-prefill-chunk: auto`, `RADIANCE_HY4_PIPE=1`. No `prefix-cache-dir`, so nothing persists between runs.
- A fresh server for every run. Session 1: ON OFF OFF ON ON OFF (runs 1-6, all phases). Session 2: OFF ON ON OFF OFF
  ON (runs 7-12; only the four phases whose spread was widest). Workload: `scripts/backlog/x06_fp5.py`; table:
  `x06_fp5_agg.py`. PCIe AER on card 4 and its switch: no fatal or non-fatal error, and the link held Gen5 in every
  run.

- **r8** is the only row where ON is ahead per request: 33.5 of the 36 ON/OFF pairs favour ON. The phase's aggregate
  rate (decode tokens / phase wall, which takes in the prefills and the waits between turns) does not move:
  median 632.1 ON against 633.8 OFF (spread 605-681). It is a gain of at most ~3 % in per-request decode speed
  on repeated sampled answers under load, and no measurable change in throughput.
- **Greedy retries gain nothing.** The 2nd and 3rd asks decode at 247.4 / 247.3 tok/s ON and 247.2 / 247.3 OFF (ask
  1: 246.9 / 246.8). The global cache won 5 proposals a run and produced no suffix step. By `gsuffix.h`'s rule a token
  that followed its context once scores 1/2 and twice 2/3, so the path score falls below
  `draft-suffix-min-score` 0.3 after 1-2 tokens. The scheduler takes a suffix chain only when it expects more than
  the DFly2 head, which accepts about 2.4 drafts a step here. Flash-Next's +3.2 % on greedy retries does not carry
  over to Hy4's head.
- **Control:** no cost at c1 or c8 (both inside noise). At c8 ON, 14-42 lookups a run found the cache busy
  (a lookup never waits; it proposes nothing then).

### D-7: the suffix index at 64K

Card-less, `suffix_test`'s `perf_suffix_index_costs` (this PR adds the 65536-token row), on the build host's CPU:

```
    20000 tokens: build at first token 1.56 ms; per 8192-token chunk: first 0.62 ms, others at most 0.95 ms, all 1.90 ms; stash copy 0.07 ms
    65536 tokens: build at first token 5.00 ms; per 8192-token chunk: first 0.62 ms, others at most 1.44 ms, all 6.61 ms; stash copy 0.20 ms
    200000 tokens: build at first token 15.97 ms; per 8192-token chunk: first 0.62 ms, others at most 2.47 ms, all 19.60 ms; stash copy 0.52 ms
```

Before `b1088f7a`, the scheduler took 5.0 ms under its lock in one piece at the first token of a 64K prompt. Now it
takes at most 1.44 ms per committed 8192-token chunk, plus a 0.20 ms copy into the stash. The next turn takes the
index over and indexes only the 29 tokens it adds. D-7's 12 ms at 64K (0.19 us a token) is 5.0 ms on this CPU.
Served (t64): `suffix_adopted_total` +1 in each of the 6 runs. Turn 2's TTFT is 0.033 / 0.033 / 0.043 s ON and
0.034 / 0.035 / 0.043 s OFF, after a 58419-token turn 1 at 11.32-11.35 s in both arms.

### Parity

- Greedy, short prompts (rg): all 12 texts are identical in all 6 runs of session 1, ON and OFF: `daf959ebc7a0` x3,
  `747b2a9da42c` x3, `ab454c1041e5` x3, `8ddc031c1017` x3.
- Greedy, 58K prompt (t64): turn 1's 8 tokens differ from run to run **within each arm**: OFF r2 `b13bf01d8b3e`, r3
  `63ce29e67b65`, r6 `5e3c4a52b9ad`; ON r1 `63ce29e67b65` (the same as OFF r3), r4 `d01caf3c47c3`, r5 `147d1adb2eb3`.
  The same 58K prompt is not run-to-run deterministic on this tree with either setting, so the switch is not the
  cause. This is outside X-06 and is recorded here for the record.
- Sampled: a coupled verify's text depends on what was proposed. Even within one arm, run-to-run equality is partial
  (rs: 4/12 ON, 7/12 OFF the same in all three runs of session 1; r8, c1, c8: 0). The global cache adds
  proposals, so more requests differ ON. That is the item's stated bound: sampled output may differ only where
  proposals differ.

## 2. FP-6: DARTree sizing for DFly2 (go / no-go for FP-9)

Data: the same tree, the ON config, with a local logging patch that is not part of this PR. It is env-gated
(`RADIANCE_DEBUG_FP6_LOG`, 15 lines in `Engine::bind_couple`) and writes draft 1's coupled law Q_1 (its 8 ids and q,
and the bound output position) for every sampled verify. The target law P at the same position is taken from the
response's `logprobs` (top 20, raw distribution; `scripts/backlog/x06_fp6.py`). The run is c1: 96 code requests at
T 1.0 (P exact) and 48 at T 0.9 (P rescaled from the top 20, the tail outside them at its bound midpoint), 256 tokens
each. `scripts/backlog/x06_fp6_replay.py` replays recursive rejection sampling (`abi/rad_mtp_rrs.h`) with k = 1, 2, 3
children drawn without replacement from Q_1. It computes exact expectations over the draw orders. The join checks
out: Q_1's draft equals the emitted token at 0.771 of the positions, and the replayed depth-1 acceptance is 0.770.
The served counter gives 0.739 over the 5919 verifies that reached position 1.

Baseline for the net column: the chain's c1 control phase (OFF): 2.958 tokens a step, 13.2 ms a decode step.

- Gate in `flashnext-port.md` FP-6: k = 2 must add >= 0.12 tokens a step at c1. **It adds 0.085 (T 1.0) and 0.089
  (T 0.9).** k = 3 reaches 0.121 / 0.126, but it needs two extra rows.
- Net at c1: -4.4 % (k = 2) and -9.6 % (k = 3) at 1.0 ms a row. To break even, a leaf sibling's row must cost at most
  0.38-0.40 ms (k = 2), or 0.27-0.28 ms per row (k = 3). The upper bound gives an accepted sibling a branch as deep
  as the chain (+1.54 drafts after it). That adds 0.216-0.229 tokens a step, but it needs about 5 more rows, so its
  break-even is below 0.2 ms a row.
- At c >= 4, every sequence adds its sibling rows to a step that already verifies 4-8 chains. The tokens a sequence
  gains stay the same, so the net gets worse with load, as the item expects (<= 0).

## Verdict

- FP-5 (merged in #232): no regression anywhere. Control c1 / c8 are inside noise. Greedy is byte-identical where the
  tree is deterministic. The gain is at most ~3 % per-request decode speed on sampled retries at c8, and 0 on greedy
  and sampled retries at c1. That is within the item's +0-2 % sampled; the code stays as merged.
- D-7: the 64K index costs 5.0 ms in one piece under the lock before `b1088f7a`, and <= 1.44 ms a chunk after; the
  take-over fires on every next turn.
- **FP-6: no-go for FP-9.** A depth-1 sibling adds 0.085-0.089 tokens a step, under the 0.12 gate, and costs -4.4 %
  at c1 at the 1.0 ms row price.
