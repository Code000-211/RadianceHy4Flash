## Why verify heights

Speculative decoding (DFly2 here) verifies several drafted tokens a sequence, so a verify step at a few sequences runs
the router GEMM at 17–63 rows. Hy4's router (`glm_router.weight`, N 512 K 3072, bf16 weight) runs replicated below
`GlmTp::kSplitRows` (256 rows), so its verify pass is N 512 at every TP width; from 256 rows (prefill) it is
column-split (N 128 a rank at TP 4: the `N=128` router row in the c8 profile table is its one mixed prefill step). The change sends 17–63
rows to the staged form at N ≥ 512, and at N 256–511 from 32 rows; every other shape keeps its form, so rows at
N 128, below 32 rows at N 256 and at 16 or 64 rows are controls.

## Order (interleaved)

Every row set ran **A1 B1 B2 A2 A3 B3** (A = before, B = after): three runs a side, alternating so that drift does not
favour one side. Each session ran, in order: card 0 `--perff32` over 20 shapes, `--case gemm_nt_f32_bf16`,
`rad-kbench --op gemm_nt_f32` (max-tok 63 and 48), a TP 4 profile-ops server (c1 and c8 probes), then a TP 4 e2e server
(greedy parity, then three probe rounds). The full `r4d_selftest --jobs 1` ran once a side (A, then B) before the
sessions.
