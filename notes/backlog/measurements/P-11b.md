# P-11b measurement: the unused arena transients of the Hy4 plan

Status: **measured** — the plan (card-less, both shapes) and the lane (throughput, TTFT and output parity,
two windows of three interleaved runs an arm, the second with the order inside the pair reversed). The change
drops five of the transients the plan charged for the whole program and names every one that stays, with the
rule that asks for it.

## The plan, card-less (`radiance --config … --debug-graph`, no weight loaded)

The card asked for this: the dump now names each buffer it charges for the whole program, so the list below is
read, not inferred. `core/build/rad_bufplan.cpp` charges a transient the whole program when no op of the
declared list names it; `Builder::finish_buffer_liveness()` used to be the only place that knew which buffers
those were and said nothing, so `BufferInfo::no_op_use` now carries it to the dump. The configs are two lines
each — `tp: 2` / `tp: 4`, `max-num-batched-tokens: 2048` / `8192`, `debug-graph: true` — on the served model.

```
TP2, 2048 rows      before                                                    after
---- buffer plan: arena 3.24 GiB, scratch 41.13 MiB                    arena 3.21 GiB, scratch 41.13 MiB
  15 transient buffer(s), 123.72 MiB, had no declared use              10 transient buffer(s), 84.59 MiB, had no declared use

TP4, 8192 rows      before                                                    after
---- buffer plan: arena 11.24 GiB, scratch 20.57 MiB                   arena 11.14 GiB, scratch 20.57 MiB
  15 transient buffer(s), 268.62 MiB, had no declared use              10 transient buffer(s), 172.12 MiB, had no declared use
```

The five planes the change takes away, at both shapes (`TP2 / TP4`):

```
dense_ff        27.00 MiB /  54.00 MiB   declared by the first dense MLP that takes the unfused pair
moe.shared_ff    3.00 MiB /   6.00 MiB   the same rule for the shared expert of a MoE layer
eg.rows.rt       6.00 MiB /  24.00 MiB   the Engram round trip's bf16 rows
eg.rows.q        3.00 MiB /  12.00 MiB   its E4M3 codes
eg.rows.s      128.00 KiB / 512.00 KiB   its row scales
                39.13 MiB /  96.50 MiB   123.72 − 84.59 and 268.62 − 172.12, to the byte
```

The served u3 stores the Engram table as E4M3 rows, so its rows take no round trip and the three planes were
pure arena; the two product planes are written only by the unfused `silu_mul` + `had_quant_act_i8g` pair, and
the served recipe folds the gate (`gemm_nt_q_gated`), so nothing named either of them. The arena line drops by
0.03 and 0.10 GiB, which is the two sums within the line's two-decimal rounding (39.13 MiB = 0.038 GiB,
96.50 MiB = 0.094 GiB): the arena is the *peak live* of the packed set, so a plane that was live everywhere
returns its bytes to the packing and the peak falls by its size.

**The fused gate is the reason `arch/common/rad_fp8.h` is in this diff.** With a plane dropped and the block
untouched, the intermediate dump lost the fold — `trunk_codes.gated.6912.128.q8` (13.50 MiB) and its `.s8`
went dead beside it, because `GateQuantFP8::declare` refused a wire with no bf16 plane even on the row that
writes the codes alone (`want_x` false, `rad_op_writes(b, op, wr, want_x ? 3 : 2)`), so the dense MLP fell back
to the unfused pair. Asking for the plane where a form names it — and only there, with `want_x && !a.x` still
`RAD_E_INVAL` — gave the fold back; the numbers above are with the fold.

## The 10 planes that stay, and why each one does

Read from the same dump; each chased to the code that asks for it. `hyv4flash_arch_test`'s
`no_transient_is_declared_that_no_op_reads` pins the same residue per plan, by name and by bytes.

| plane (TP2 / TP4) | why it is still declared |
|---|---|
| `moe.expert_ff` 48 / 96 MiB | the routed arm's bf16 product. `silu_mul` writes it for bf16 experts (`rad_block_moe_fp8.h`, the `bf16` arm of `GateQuantFP8::declare`) and the rotated chain writes it whether or not a consumer asked; the wire that declares it cannot see a container's `expert_bf16` mix |
| `moe.expert_ff.q` / `.s` 24 MiB + 768 KiB / 48 + 1.5 MiB | its E4M3 codes. `down_codebook_fp8` / `down_supported` (`rad_block_moe_fp8.h`) ask for them — the mixed recipe of an IQR gate_up behind a w6 down with them — while no op of an int8 plan names them |
| `moe.latent.q` / `.s` 3 MiB + 96 KiB / 12 + 384 KiB | same: `MoeFP8::declare` refuses a wire whose latent carries no codes; its read is the rotated int8 pair |
| `ix.stage` 768 KiB / 2.25 MiB | staged raw keys of the closing group; issued only when the library does not serve the fused key side (`qsa_work_pool_tail`), which the wire cannot know for a layer's geometry |
| `sampler.cand_gathered/pairs/idx/val` 8 / 12 MiB | the sampler declares its ops with no operand lists at all (`core/sample/sampler.cpp`), so no plan can name them; a core change, outside this card |

The four code planes and `moe.expert_ff` together are 79.84 MiB of the 84.59 at TP2 and 157.88 of the 172.12 at
TP4: they are the card's remaining sum, and taking them means changing what `MoeFP8` requires of a quantised
expert's wire, not what the arch declares — `quantised_experts_are_served_clamped` and
`quantised_experts_are_sliced_at_more_ranks` are the tests of that rule and they refuse a wire without the
pair, which is why a first attempt at dropping them in this round was put back.

The issue quotes 14 planes and 115 MiB at TP2 / 255 MiB at TP4 (from #81). The dump at the merge base counts 15
and 123.72 / 268.62 MiB; the difference is the sampler's four planes and `ix.stage` (8.75 MiB at TP2), which the
issue's list does not carry. The dump is the authority here.

## One config, both arms — and one thing this measurement does not claim

An earlier window ran each arm with the `scripts/backlog/nospec.yaml` **of its own tree**, which is the same
file in both trees and asks for `max-model-len: 65536`. The base boot came up clamped —
`I --max-model-len 8192 [models.hy4-flash.max-model-len]`, `kv cache 1.10 GiB … backs 8 sequences all at
8192 tokens` — while the head boot served the requested 65536 (`kv cache 7.33 GiB`, `9 checkpoint slots a
sequence` instead of 5). Its rows are therefore not comparable: the arms differed in context length, KV size
and checkpoint slots, not only in the plan. Those rows are left out here, and the quoted lane writes
one value into one YAML both arms read.

What the discarded window does support is an **observation, not a claim**: on this rig at this cap, the
merge base could not afford the configured 65,536-token worst case where the head could. Nothing here says
how much of that is the freed arena and how much is the startup's own auto-sizing reacting to it; the
engine logs no clamp line, so it is not measured. It is written down because a reviewer may see the same
thing and wonder.

## The lane: the arena the server reports at startup

Both arms, `--max-model-len 8192`, verbatim (identical in all twelve boots):

```
before  I activation arena: 256 tokens use 159.91 MiB, 1024 tokens use 638.02 MiB of 1.25 GiB
                          (the fixed region is 288.50 KiB); the rest is lent to the expert slab
                          while the steps are that small
after   I activation arena: 155.02 MiB … 618.46 MiB of 1.21 GiB          (same sentence)
```

(the second line is abbreviated here; the log line is the same sentence with 155.02 MiB, 618.46 MiB and
1.21 GiB.) The fixed region is the same 288.50 KiB on both sides, so the whole difference is packed
transients: **4.89 MiB at the 256-row level, 19.56 MiB at the 1024-row level**.

Those are the five planes at those row counts, to the byte: `dense_ff` {T, 6912} bf16 is 3.375 / 13.50 MiB,
`moe.shared_ff` {T, 768} bf16 is 0.375 / 1.50 MiB, and the Engram trio {T, 1536} bf16 + {T, 768} e4m3 +
{T, 1} f32 is 0.75 + 0.375 + 0.016 / 3.00 + 1.50 + 0.062 MiB. 3.375 + 0.375 + 1.141 = 4.891 and
13.50 + 1.50 + 4.562 = 19.562. The lane's own line therefore repeats what the card-less plan dump says about
the same five planes, at two row counts, on the real boot.

## Raw rows — `c1` and `c8`, two windows of three interleaved runs an arm (A = before, B = after)

The first window boots the arms A then B in each pair; the second boots them B then A, because in the first
every B `c1` came out below every A `c1` and that had to be told apart from a real difference.

```
window 1, 2026-11-26 18:48–18:55 (A booted first in each pair)
  run  c1 tok/s   c8 tok/s        c1 ttft   c8 first token
  A7   71.619     311.903         0.077     0.072
  B7   71.207     308.660         0.079     0.071
  A8   71.395     307.625         0.075     0.071
  B8   71.309     309.201         0.080     0.071
  A9   71.415     306.735         0.073     0.072
  B9   71.123     306.740         0.075     0.072
  median of the arm   A 71.415 / 307.625     B 71.207 / 308.660

window 2, 2026-11-26 18:57–19:03 (B booted first in each pair)
  run  c1 tok/s   c8 tok/s        c1 ttft   c8 first token
  B10  71.231     308.818         0.077     0.072
  A10  71.216     309.776         0.072     0.071
  B11  71.256     310.525         0.073     0.072
  A11  71.234     309.917         0.073     0.071
  B12  71.223     308.459         0.073     0.072
  A12  71.214     311.245         0.073     0.071
  median of the arm   A 71.234 / 309.917     B 71.231 / 308.818
```

The `c1` gap of the first window (−0.29 % of the medians) does not survive the reversed order: booted first,
B is level with A (−0.004 %). Whichever arm boots first in a pair is the faster one on `c1` by about 0.3 %,
which is the size of the effect being looked for, so the ordering explains the gap and the arms do not.
Pooled over the twelve runs the medians are A 71.315 / 309.847 and B 71.227 / 308.739 (−0.12 % and −0.36 %),
inside the spread of a single arm (A alone spans 71.214–71.619 and 306.735–311.903). TTFT: the first token of
a `c8` batch is 0.071 s on both sides in both windows, and the seven clients behind it see 0.275–0.279 s in
window 1 and 0.269–0.272 s in window 2 — the same figures for both arms of a window, so they are a property
of the window, not of the change. `c1`'s single-token TTFT is 0.073–0.080 with no pattern by arm.

## Output parity

The greedy phase's four completions are byte-identical across the arms: `sha256(json.dumps(texts))` =
**f8a826ab4b932e6b** on all twelve runs (A7–A9, B7–B9, A10–A12, B10–B12), each boot printing the same four
records. In the discarded window the arms differed (`c3c7119f…` against `f8a826ab…`) because they ran
different context lengths, not because a kernel changed.

## What the numbers say, and what they do not

- **Measured:** the plan's charged set and the arena it packs to, both shapes, card-less and read from the
  dump rather than inferred; the startup arena line and its two levels, six boots an arm; `c1` and `c8`
  throughput and TTFT, two windows of three interleaved runs an arm with the order inside the pair reversed
  in the second; byte-identical greedy output on all twelve runs.
- **The merge bar:** lossless — the output is byte-identical; the item's target is memory, and it moved by
  the amount the plan says it should (39.13 MiB charged away at TP2/2048, 96.50 at TP4/8192, and 19.56 MiB
  off the 1024-row level of the lane's arena, both the plan's arithmetic and the boot agreeing to the byte);
  end to end `c1` differs by −0.12 % and `c8` by −0.36 % of the medians over the twelve runs, inside the
  spread one arm shows within itself (A alone: 71.214–71.619 and 306.735–311.903) and of the same size as
  the effect of booting first in a pair (+0.29 % on `c1` for the arm booted first in window 1, gone in the
  reversed window 2), so nothing is claimed for speed in either direction.
  A kernel-level ms gain is not what this item targets: no op got faster, one fewer plane gets reserved.
- **Not measured:** the 65536-vs-8192 boot difference (§above) — one boot of each side in the discarded
  window, no clamp line in the log, so it is an observation; the TP4 lane (the rig runs TP2, and the TP4
  figure is the card-less plan, not a run); whether the freed arena is spent on the expert slab or handed
  back — the lane's `mover:` lines differ between the arms for that reason and are not quoted.
- **Limits of the dumps:** they run on the host backend with no weight loaded, which is what makes them
  card-less; they state what the declare pass reserves, not what a boot maps.
