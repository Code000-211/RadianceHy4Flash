Status: **measured** — the plan (card-less, both shapes) and the lane (throughput, TTFT and output parity,
three interleaved runs an arm). The change drops six of the transients the plan charged for the whole
program and names every one that stays.

## The plan, card-less (`radiance --config … --debug-graph`, no weight loaded)

The card asked for this: the dump now names each buffer it charges for the whole program, so the list below is
read, not inferred. `core/build/rad_bufplan.cpp` charges a transient the whole program when no op of the
declared list names it; `Builder::finish_buffer_liveness()` used to be the only place that knew which buffers
those were and said nothing, so `BufferInfo::no_op_use` now carries it to the dump.

```
TP2, 2048 rows      before                                                    after
---- buffer plan: arena 3.24 GiB, scratch 41.13 MiB                    arena 3.21 GiB, scratch 41.13 MiB
  15 transient buffer(s), 123.72 MiB, had no declared use              11 transient buffer(s), 87.59 MiB, had no declared use

TP4, 8192 rows      before                                                    after
---- buffer plan: arena 11.24 GiB, scratch 20.57 MiB                   arena 11.15 GiB, scratch 20.57 MiB
  15 transient buffer(s), 268.62 MiB, had no declared use              11 transient buffer(s), 178.12 MiB, had no declared use
```

The four planes the change takes away, at both shapes (`TP2 / TP4`):

```
dense_ff        27.00 MiB / 54.00 MiB   declared by the first dense MLP that takes the unfused pair
eg.rows.rt       6.00 MiB / 24.00 MiB   the Engram round trip's bf16 rows
eg.rows.q        3.00 MiB / 12.00 MiB   its E4M3 codes
eg.rows.s      128.00 KiB / 512.00 KiB  its row scales
                36.13 MiB / 90.50 MiB   123.72 − 87.59 and 268.62 − 178.12, to the byte
```

The served u3 stores the Engram table as E4M3 rows, so its rows take no round trip and the three planes were
pure arena; the dense MLP's product plane is written only by the unfused `silu_mul` + `had_quant_act_i8g` pair,
and the served recipe folds the gate (`gemm_nt_q_gated`), so nothing named it either. The arena line drops by
0.03 and 0.09 GiB, which is the two sums within the line's two-decimal rounding (36.13 MiB = 0.035 GiB,
90.50 MiB = 0.088 GiB): the arena is the *peak live* of the packed set, so a plane that was live everywhere
returns its bytes to the packing and the peak falls by its size.

**The fused gate is the reason `arch/common/rad_fp8.h` is in this diff.** With the plane dropped and the block
untouched, the intermediate dump lost the fold — `trunk_codes.gated.6912.128.q8` (13.50 MiB) and its `.s8`
went dead beside it, because `GateQuantFP8::declare` refused a wire with no bf16 plane even on the row that
writes the codes alone (`want_x` false, `rad_op_writes(b, op, wr, want_x ? 3 : 2)`), so the dense MLP fell back
to the unfused pair. Asking for the plane only in the two forms that name it gave the fold back; the numbers
above are with the fold.

## The 11 planes that stay, and why each one does

Read from the same dump; each was chased to the code that asks for it.

| plane (TP2 / TP4) | why it is still declared |
|---|---|
| `moe.expert_ff` 48 / 96 MiB | the routed arm's bf16 product. `silu_mul` writes it for bf16 experts (`rad_block_moe_fp8.h`, the `bf16` arm of `GateQuantFP8::declare`) and the rotated chain writes it whether or not a consumer asked; the wire that declares it cannot see a container's `expert_bf16` mix |
| `moe.expert_ff.q` / `.s` 24 MiB + 768 KiB / 48 + 1.5 | its E4M3 codes. `down_codebook_fp8` / `down_supported` (`rad_block_moe_fp8.h`) ask for them — the mixed recipe of an IQR gate_up behind a w6 down with them — while no op of an int8 plan names them |
| `moe.latent.q` / `.s` 3 MiB + 96 KiB / 12 + 384 KiB | same: `MoeFP8::declare` refuses a wire whose latent carries no codes; its read is the rotated int8 pair |
| `moe.shared_ff` 3 / 6 MiB | the shared expert's product plane, the same unfused pair as `dense_ff` was; `MoeWire::declare` cannot see `ffn_down_shexp`'s encoding, so a lazy slot of the kind `dense_ff` now uses is the fix and it is not in this diff |
| `ix.stage` 768 KiB / 2.25 MiB | staged raw keys of the closing group; issued only when the library does not serve the fused key side (`qsa_work_pool_tail`), which the wire cannot know for a layer's geometry |
| `sampler.cand_gathered/pairs/idx/val` 8 / 12 MiB | the sampler declares its ops with no operand lists at all (`core/sample/sampler.cpp`), so no plan can name them; a core change, outside this card |

The issue quotes 14 planes and 115 MiB at TP2 / 255 MiB at TP4 (from #81). The dump at the merge base counts 15
and 123.72 / 268.62 MiB; the difference is the sampler's four planes and `ix.stage` (8.75 MiB at TP2), which the
issue's list does not carry. The dump is the authority here, and `hyv4flash_arch_test`'s new
`no_transient_is_declared_that_no_op_reads` pins the residue per plan so a new plane fails by its name.

## One config, both arms — and one thing this measurement does not claim

The first window ran each arm with the `scripts/backlog/nospec.yaml` **of its own tree**, which is the same
file in both trees and asks for `max-model-len: 65536`. The base boot came up clamped —
`I --max-model-len 8192 [models.hy4-flash.max-model-len]`, `kv cache 1.10 GiB … backs 8 sequences all at
8192 tokens` — while the head boot served the requested 65536 (`kv cache 7.33 GiB`, `9 checkpoint slots a
sequence` instead of 5). Its rows are therefore not comparable: the arms differed in context length, KV size
and checkpoint slots, not only in the plan. Those rows are left out here, and the quoted lane below writes
one value into one YAML both arms read.

What the discarded window does support is an **observation, not a claim**: on this rig at this cap, the
merge base could not afford the configured 65,536-token worst case where the head could. Nothing here says
how much of that is the 27 MiB plane and how much is the startup's own auto-sizing reacting to it; the
engine logs no clamp line, so it is not measured. It is written down because a reviewer may see the same
thing and wonder.

## The lane: the arena the server reports at startup

Both arms, `--max-model-len 8192`, verbatim (identical in all three boots of an arm):

```
before  I activation arena: 256 tokens use 159.91 MiB, 1024 tokens use 638.02 MiB of 1.25 GiB
            (the fixed region is 288.50 KiB); the rest is lent to the expert slab …
after   I activation arena: 256 tokens use 155.40 MiB, 1024 tokens use 619.96 MiB of 1.21 GiB
            (the fixed region is 288.50 KiB); the rest is lent to the expert slab …
```

The level for 1024-row steps falls by 18.06 MiB and the one for 256 rows by 4.51 MiB; the total line falls
by 0.04 GiB. At 8192-token context the dense MLP's plane is half the size it was at the 2048-row batch of
§"The plan" (`max-num-batched-tokens 2048` bounds the rows a step carries), which is why the lane's numbers
are smaller than the plan dump's 36.13 MiB — they are the same plane seen at the shapes this config runs.

## Output parity

The greedy phase's four completions are byte-identical across the arms: `sha256(json.dumps(texts))` =
**`f8a826ab4b932e6b`** on all six runs (A4, A5, A6, B4, B5, B6), each boot printing the same four records.
In the discarded window the arms differed (`c3c7119f…` against `f8a826ab…`) because they ran different
context lengths, not because a kernel changed.

## What the numbers say, and what they do not

- **Measured:** the plan's charged set and the arena it packs to, both shapes, card-less and read from the
  dump rather than inferred; the startup arena line and its two levels, three boots an arm; `c1` and `c8`
  throughput and TTFT, three interleaved runs an arm; byte-identical greedy output.
- **The merge bar:** lossless — the output is byte-identical; the item's target is memory, and it moved by
  the amount the plan says it should (36.13 MiB charged away at TP2/2048, 90.50 at TP4/8192, and 18.06 MiB
  off the 1024-row level of the lane's arena); end to end `c1` differs by 0.05 % and `c8` by 0.03 %, inside
  the spread the arms show within themselves (c1 71.338–71.391, c8 308.24–310.96), so nothing is claimed
  for speed in either direction. A kernel-level ms gain is not what this item targets: no op got faster,
  one fewer plane gets reserved.
- **Not measured:** the 65536-vs-8192 boot difference (§above) — one boot of each side in the discarded
  window, no clamp line in the log, so it is an observation; the TP4 lane (the rig runs TP2, and the TP4
  figure is the card-less plan, not a run); whether the freed arena is spent on the expert slab or handed
  back — the lane's `mover:` lines differ between the arms for that reason and are not quoted.
- **Limits of the dumps:** they run on the host backend with no weight loaded, which is what makes them
  card-less; they state what the declare pass reserves, not what a boot maps.
