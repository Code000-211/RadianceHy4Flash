## Method

`scripts/backlog/run.sh <tag> <cfg> <phases> [ENV=VALUE...]`, which takes the card reservation
itself and runs on the lane's cards; nothing else of mine touched the cards while a run held them.

- **Served step, interleaved**: `coupled03.yaml`, phases `c1,c8,greedy`, tags `b1 a1 b2 a2 b3 a3`
  (before, after, ...), 3 runs a side, 1m40s a run.
- **Op rows, interleaved**: `cprof.yaml`, phases `c1,c8`, `RADIANCE_PROFILE_EVERY=1`, tags
  `pb1 pa1 pb2 pa2 pb3 pa3`, 3 runs a side. A run dumps the per-op table every step
  (cumulative), so consecutive dumps were differenced into a step's delta, a step whose delta
  total is ≥ 200 ms was dropped as a prefill chunk, and the report is the median a decode step over
  the last 40 decode steps of the phase (the warmup dropped). Rows are keyed by op index as well as
  name, because a chain round declares its own op: the trunk's output row (declared first, `#2805`)
  is told apart from the rounds' rows (`#3003`…), and a round's cost is the call's µs, not the sum
  over the step's 5 rounds.
- **Taps**: `coupled03.yaml`, phase `c1`, `RADIANCE_HY4_TAPS=1
  RADIANCE_DUMP_BUF=dbg.dfly.cand_idx.4,dbg.dfly.cand_val.4 RADIANCE_LOG=trace`, tags `tb` (before),
  `ta` and `ta2` (after, twice). The buffer probe prints one hash a step for each dumped buffer.

The card's `max-num-seqs: 8` lane runs the fused op on its `c1` rounds only: `logits_topk` serves
at most 2 rows a call (`RAD_RANGE("M", 1, min(S,2))`, the band the head's matvec body covers), and
a round takes it when the round's own row count `n <= 2` -- which is what an `n = 1` draft round at
c1 is. The `c8` phase's rounds have 8 rows and keep `logits_gemm` + `cast_row_topk`, unchanged code,
which is why the `c8` rows below are the control that the pair path did not regress.

## 5. The `row_topk` kbench rows

The fixture's `row_topk` rows timed the same in both trees, which is the point -- the kernel moved
into `libr4d/r4d_topk.h` without its body changing, so the rows it serves must not move. Both sides
run `rad-kbench --home build/radiance_home --kernels libr4d --ref libr4d --timing-only --op row_topk
--op cast_row_topk --op row_topk_merge --report <file>`, `--timing-only` because `rad-kbench` refuses
to load the shipped reference beside `libr4d` at this HEAD (see below), so the numbers rank speed
only; the correctness of the same rows is the emulator test's and `kbench_ref`'s.

Every row is inside its own interval across the two trees: the pair path did not move, and the
fused head's own row is not in the fixture -- the fixture reaches no `logits_topk`, `cast_row_topk`
or `row_topk_merge` case (it is a recording of another model's graph), and a new fixture or a
`rad-kbench` row is a locked path (`AGENTS.md`), so the fused op is timed by profile-ops above.

Two things about the kbench load, both from the merge base as well as this head:

```
E op 'attn_dense' has two different schemas: 'libr4d' fixed it first, 'libref' disagrees
  (parameter 'max_seqlen' has role 2 vs 0) -- refusing 'libref'
```

so `--kernels libr4d:libref` (the check-and-time run) cannot load, and `--kernels libr4d` alone
stops with "no kernel library loaded declares itself a reference implementation". Hence `--ref
libr4d --timing-only`. `kbench_ref` (the reference alone, replaying the fixture) passes in both
trees.

## Verdict against the merge bar (`notes/backlog/CARDS.md` §2)

1. **Byte-identical output**: yes -- the four served generations are identical in all six runs, the
   drafter's tokens a step and hit rate match, and the candidate taps agree on every step from the
   first draft round on (716 of 718 lines; the two that differ are unwritten buffer bytes, which
   differ between two runs of the same code too).
2. **The targeted op is measurably faster**: yes -- a c1 draft round 339.5 → 330.1 µs (2.8 % a
   round, 3 runs a side, medians of the same phase), from `cast_row_topk`'s 19.6 µs leaving the
   round and 10.2 µs of top-k moving into the head's kernel; the c8 round is unchanged, and so are
   the `row_topk` kbench rows (§5), which the fused path no longer calls.
3. **End to end not worse**: yes -- c1's step is 0.23 % shorter (medians) with the same tokens a
   step, c8 is inside its own 35–43 ms spread, TTFT identical.
