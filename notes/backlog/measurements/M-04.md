# M-04 (stager ring sizing, partial heavy layers): a served A/B that does not separate the arms

The item asks for three changes in `core/mem` and `core/place` and names its verify: `/stats experts
stage_overflow` per chunk in the longctx sweep, plus prefill tok/s. This file is the measurement of
that; `notes/backlog/closed/M-04.md` is the verdict.

- After: `1595eaab` (place: two-part heavy layer, heat-first order) + `00542790` (mem: ring from the
  heaviest routed layer, ~1 GiB bound). Both are reverted by `5240756c` and `303ec065` in the same
  branch, so the branch's own tree carries no code from this item.

  each), power cap 210 W read back on both cards before every run, no container: each arm's own

  AMD clang from that tree). 2026-11-25.

## 2. The counters the item names, per chunk

`stage_overflow` is 0 in all seven runs, on both arms, at both placements, in every chunk. The
"units no buffer had room for (read in place)" is the same counter. So the traffic the item wants to
rescue -- "819-950 units (1.2-1.4 GiB) a chunk" in the audit's sweep -- does not occur on this lane,
and the change had nothing to move: the base already stages every pooled unit ahead of the layer that
reads it, only later than the change does.

The arithmetic, from `m04-base` (the same file the audit used, 8 x 46K): a routed layer has 512
units of 1.03 MiB = 527 MiB, of which 15 % is pooled on average (the mean is 432.5 residents) and 35 %
for the coldest layer (344 residents), so the most any layer pools is 512 - 344 = 168 units = 173 MiB.
The ring's half is 300.14 MiB: `f x layer_max` with `f` ~ 30 % of the plan's 24.70 GiB elastic slab
against the 17.38 GiB of experts before the ring is taken, and `layer_max` ~ 1013 MiB for the largest
routed layer, which is larger than a typical layer's whole 527 MiB. The half
is therefore 1.7 x the largest pooled layer and ~3.7 x the average one (mean 432.5 residents ->
79 units pooled), and the "a layer above ring/2 is not staged ahead" path is never reached. That is
why the audit's sweep overflowed and this one does not: there `ring/2` was 261 MiB and the coldest
resident layer 255 units, i.e. 257 pooled units = 265 MiB, just over it.

## 3. What the change did move

- Ring: 1.00 GiB instead of 520-600 MiB (the item's ~1 GiB bound), paid out of the experts' share:
  experts 16.17 / 15.98 GiB in the two new runs against 16.79 / 17.15 / 18.46 GiB in the base runs
  (part of that spread is the "already held" figure, 341 MiB to 2.34 GiB, which moves with the
  previous run's leftovers). At the same `already held` (341 MiB) the two 16-session runs differ by
  ring only: experts 10.83 -> 10.70 GiB, ring 883.75 MiB -> 1.00 GiB.
- Staged units: 923416 / 948535 for the new arm against 857139 / 802714 / 629550 for the base. The
  base's own spread (-27 % between two runs of the *same* binary) is larger than the difference
  between the arms, so this is residency and heat history, not the change.
- Copies: 149025 / 175007 new against 166108 / 129012 / 90918 base -- same story, no direction.
- The two-part heavy layer and the heat-first order change no counter on this lane, because no layer
  is ever heavier than the ring's half and no unit is ever left behind (both are only visible when a
  layer is > ring/2, which is unit-tested in `tests/place_test.cpp` on the change's commits).

## 4. Noise, and why this A/B cannot separate the arms

The same binary, back to back, moves prefill by 4.9 % (`m04-b2` 3053 -> `m04-b3` 3204 tok/s),
decode by 76 % (115.2 -> 202.3 tok/s) and median TTFT by 14 % (78.1 -> 67.2 s). The medians of the
two arms are inside that:

- prefill tok/s: base 2990 / 3053 / 3204, median 3053; new 3202 / 3022, median 3112 (+1.9 %);
  the pairs disagree in sign (+4.9 %, -5.7 %).
- prefill step seconds: base 90.5 / 92.7 / 91.2, median 91.2; new 89.6 / 90.7, median 90.2 (-1.1 %).
- median TTFT: base 78.1 / 76.3 / 67.2, median 76.3; new 71.5 / 76.1, median 73.8 (-3.3 %).
- the second placement (16 sessions, 41 % expert residency): 3625 -> 3598 tok/s (-0.7 %).

Nothing here reaches the lane's own run-to-run spread, on either side. A prefill gain of the item's
"+5-15 %" would have to come from the in-place reads it removes; that traffic is 0 on this lane, so
the gain cannot be produced here, and the change as delivered is a wash -- neither the item's win nor
a regression. That is what closes the item: see `notes/backlog/closed/M-04.md`.

## 5. What was not run

- No `stamps` / `rad-kbench` row: the change touches no kernel and no op the stamps attribute (it
  moves copies between host and card inside `core/place`), so there is no per-op row to point at.
  Prefill step seconds in §1 are the engine's own per-step timing.
- No KL and no output parity row: staging copies expert bytes, it does not change what is read or in
  which order a kernel sums, so no arm can differ numerically in a way a KL measurement would see.
  The probe's per-request texts are not committed with these runs (the lane keeps `gen` counts, not
  text, for `longctx`).
- No TP4 measurement: the lane has two cards and the change is not about tensor parallelism.
