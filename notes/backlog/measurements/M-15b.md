# M-15b: KV loan compaction under eviction pressure, on a pool backing 59 % of the worst case

The change (`071ccf00`) moves the highest cache-only blocks down into the free holes under the KV
pool's held top when, since the pool was last compact, an eviction has happened and the holes reach
`RADIANCE_KV_COMPACT_MIB` (256 by default), so the loan can lend the space they leave
(`../closed/M-15.md` for why the holes are there). Lossless: nothing is evicted by a move.

- Machine: one host, 2 x AMD Radeon AI PRO R9700 (gfx1201, 32 GiB, PCI id 0x7551, VBIOS
  113-48WD6SHD1-P02), TP2, `cap 210 W` read back on both cards before every run; 16 cores, 70 GB RAM.
  Host kernel 7.3.5-arch1-1 (in-tree amdgpu). Measured by the PR's author.
- Before: `337fbb97` (the base). After: `071ccf00` (the change; this file comes on top and changes
  nothing else). The binaries were built from `93fadad7`, the same tree as `071ccf00`: the commit was
  only re-authored afterwards (`git diff 93fadad7 071ccf00` is empty; `93fadad7` is a local commit,
  not pushed). Same host, same settings, same container, same model file.
- Build and run container: `rocm/dev-ubuntu-24.04:10.1.0-full`
  (`sha256:5ed1362ea542a928651e4c710b44024ebe98870f74159cb70f0265aec8ef0abe`, HIP 7.16.26385) with the

## The eviction case (`long8`, prefix-cache host tier off)

| view | holes MiB, before | holes MiB, after | slab MiB, before | slab MiB, after | expert VRAM units, before | after |
|---|---|---|---|---|---|---|
| finished / idle | 620-701 | **206-243** | 229-360 | **717-776** | 15,514-15,597 | **15,873-15,897** |
| demanded | 620-701 | 206-241 | 1,768-1,925 | **2,281-2,340** | 16,587-16,689 | **16,964-16,988** |
| resume | 973-1,002 | **221-252** | **0.0** | **674-747** | 15,429-15,431 | **15,873-15,885** |

- The holes settle just under the 256 MiB bar, as the change intends (a pass stops when they are
  under it), from 620-1,002 MiB: the held top comes down from 68,742-75,981 to 60,895-61,769
  blocks. `kv_loan.compacted` says 13,138-16,071 blocks moved by the end of the batch and
  37,734-42,602 by the resume (nothing on the before arm, which has no such field).
- At `resume` the before arm's slab is at 0 MiB in every run (as M-15 found on iks-A); the after
  arm keeps 674-747 MiB lent and ~450 more expert units in VRAM in every view after the batch,
  about what the recovered holes are worth at M-15's 100 MiB = 70 units.
- Expert hit rate of the demand decode (`demand_hit`, routed resident / routed): before
  0.9488-0.9524, after 0.9527-0.9550.
- `resume_hit_tokens` varies by run on both arms (55,552-209,232 before, 75,392-150,720 after):
  which conversation is evicted depends on arrival order; no claim is made from it.
- Throughput (agg tok/s): `c8` before 278.1-280.0 (b1, the first run on a cold host, 191.0),
  after 279.0-281.9; `lctx4` decode before 47.2-54.6, after 48.5-53.3; `long8` waves inside the
  same spread. No regression beyond noise; the copies (up to 1,024 blocks a pass, one 2-D copy a
  run) did not show at this resolution.

## No regression where holes are ~0 (prefix-cache host tier on)

The local lane's served config does not fit this host; the same settings with the host tier on
(8192 MiB, as the iks lanes) are the case where a finished conversation's blocks go to host and the
holes stay near zero (0.0-1.1 MiB in every `idle` view, both arms). There the compaction is off by
design (`compacted` 0 in every view of the after arm).

- `c1`: before 73.7-73.8 tok/s (13.24-13.26 ms/step), after 73.6-73.9 (13.23-13.28).
- `c8`: before 284.3-286.3, after 282.7-283.4. The three after runs fall just under the three
  before runs (~0.6 %); the eviction runs above show the opposite order (after 279.0-281.9 vs
  before 278.1-280.0), and with the compaction off its tick reads one counter. Read as noise,
  stated as measured.
- `idle` resume TTFT 0.108-0.110 s and cold TTFT 7.61-7.66 s on both arms.

## Greedy output

The three fixed prompts are identical in all twelve runs: `d6da4fb33eed…/256`, `0699709c4be2…/256`,

one: `m15b-b3`, the **before** arm (the base binary). It therefore varies run to run on the base itself
at these settings and is not moved by the change; every after run gives `cad756fe870b…`.
