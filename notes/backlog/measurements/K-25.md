# K-25 measurements: `qsa_select` `masked 1` against `masked 0` at the served shapes

Kernel-level: one library, one card, one plane, one scratch, both variants timed in the same process, twice
each. The item's Verify names `--perfidx 16384 1`, so the shape it names is row 1 below; the decode shapes a
served run takes (c1, c8, c16) are rows 1-6c and the non-split (prefill) rows are 7-9.

- Item: K-25, `notes/backlog/optimisation-backlog.md` ("qsa_select at long context: multi-workgroup select").
- Merge base `34862f3d`; the tree measured was that base plus the two commits `066f7fd2` (libr4d: the
  `masked` parameter on `qsa_select` and on its references, the emulator test and the selftest pair) and
  `85cf7ae5` (Hy4-flash's indexer states `masked` 1 on both `qsa_select` rows). Both are dropped in the
  closing commit -- the item closes without code, see `../closed/K-25.md`; this file keeps the numbers.
- Machine `iks`: 4x Radeon AI PRO R9700 (`gfx1201`, 32 GB), Ryzen 48 cores, 112 GB, ROCm 7.16.26385,
  kernel 7.0.14-26-pve, Ubuntu 24.04.5, no container on the measuring host, no power cap set on the card.
  All rows below ran on **one** card through the card scheduler (`gpu1`, which reports it as card 3);
  rows 10-12 ran on the local host's card 0 the same way (ROCm 7.16.26385, kernel 7.0.2-6-pve, LXC).
- Placement `ram` (a `--perfidx` run serves no model: it allocates the op's own tensors).
- Build: `cmake --preset default -DRAD_WITH_HIP=ON -DRAD_GPU_TARGETS=gfx1201` (on iks: `"$RAD_CONFIGURE"`),
  `cmake --build build -j 48 --target bin/r4d_selftest radiance_home/kernels/libr4d.so`, `libr4d.so` linked
  from the same sources for every row.
- Command per row:
  `gpu1 ./build/bin/r4d_selftest build/radiance_home/kernels/libr4d.so --perfidx <ctx> <M> <iters>`
  printing `qsa_select (topk 511) masked 1  <first> / <second> us   masked 0  <first> / <second> us`:
  `sel_time()` runs masked 1, masked 0, masked 1, masked 0 over `iters` launches each, so a variant's two
  columns are its first timed call and its second one. `--perfidx` allocates the row's own scratch
  (`qsel->scratch(&sela)`, `dalloc`, `sela.scratch_bytes`), so M <= 32 at these contexts takes the row's
  **split** path -- the two-kernel `qsa_local` + `qsa_merge` form a served engine takes, which T-03 saw stamped
  24 launches a selecting pass at 63K (`T-03.md` section 1). M > 32 takes the single-workgroup kernel (rows
  7-9).

every row, with no consistent sign: 13.98 against 13.91 (row 1, +0.5 %), 13.69 against 14.06 (row 2, -2.6 %),

to 13.9 in the second column.

An earlier run, before the timing was repeated (one call each, masked 1 first), read `masked 1 15.55 us, masked
0 13.46 us` at 16384 and `masked 1 18.88, masked 0 16.50` at 65536 -- a 14-16 % "regression" that is the
first-call warm-up above and nothing else. It is recorded here so that artifact is not mistaken for a result
later.

Where the single-workgroup kernel has one workgroup a row and the table does not fit beside the score
plane, dropping the table load is 4.6x (16384 x 64); at 65536 the table is 64 KB a row and the score plane
is 4 MB for the same 64 rows, so the load has stopped being the term, and at 256 rows nothing is left of
it. Row 8's and row 9's first columns carry the same first-call warm-up as row 1: 158.66 -> 154.73 for
masked 1 beside 160.81 -> 159.16 for masked 0, and 59.68 -> 58.15 beside 63.30 -> 58.03.

## 3. The same lever on the local host (no scratch: the single-workgroup form at M = 1)

One run on the measuring pod's card 0, before `--perfidx` allocated scratch, so these are the
single-workgroup kernel at one row and they are **not** the served form (kept, as a single run, because it

```
gpu1 ./build/bin/r4d_selftest build/radiance_home/kernels/libr4d.so --perfidx 16384 1 400
  qsa_select (topk 511) masked 1          20.82 us   masked 0          92.32 us
```

That 4.4x is the same effect as row 7 -- one workgroup a row, the table load in the critical path --
and it is not what a decode step runs.

## 4. What this says about the item

- The item's premise ("1.8-3.7 ms a decode step", 12 launches a step) does not hold: the served form is
  14-19 us a launch at 16384-65536, i.e. **0.17-0.23 ms a step**, and T-03's served stamps at 63K agree
  (382-390 us for a whole selecting pass, 24 launches). The premise is high by 8-20x.
- `masked 1` is byte-identical and free, but in the split path -- the path a decode step takes -- the
  staging block prefetches a thread's pages and scores into `sv` / `pv` register slices before it computes a key
  (`r4d_qsa_select_bf16.hip:973-989`), so the page loads already ride beside the score loads and the lever buys
  nothing measurable (section 1). The 4.6x it buys in the single-workgroup kernel (section 2, row 7) is at a
  shape no long-context decode step takes, and is gone at 65536 even there.
- So the targeted op is not measurably faster in ms at the shapes the item's merge bar names, and the item
  closes without code (`../closed/K-25.md`).

  0 branch(es) unreached` -- every fixture ran masked 1 on a plane conformed to the promise (-inf wherever
  `page(s, b) < 0`) in all three forms (single, wide, split) against masked 0, and masked 0 against the
  in-file reference; and masked 1 on the unconformant plane had to select differently, which it did.

  --changed-since HEAD~2 --jobs 16`): `PASS 1 FAIL 0 INCOMPLETE 0`, 32 kernels, 0 error(s), 0 warning(s),
  49 note(s), exit 0.
