## The review's judgement points

- **The `RadQueueScratch` doc in `device.h`:** read at this head, lines 195–210 describe the derived
  charge and say the flat `n_cu * 5 MiB` bound stands when the backend cannot read code objects; there
  is no mention of the removed knob anywhere in the tree (`grep -r RADIANCE_QUEUE_SCRATCH` = 0 hits).
  The finding describes an older revision of the file.
- **Per queue vs per card:** settled in round 5 — the charge is `queue_scratch_card_bytes`, once per
  queue the plan opens (`f.n_queues` is set at `engine_bringup.cpp:2094`, incremented at 2111 and read
  at 2128, so it is set before the charge reads it). The three queues a card this lane runs did not
  fail, which is evidence the floor is enough here, not proof a per-queue overrun could not hide under
  the driver's slack.
- **Stub-backend test:** added —
  `queue_scratch_is_zero_on_the_host_backend_and_on_unified_memory` in `tests/mem_test.cpp` covers the
  host backend, unified memory and a null props (bytes 0, `metadata` false, no crash); it passes. The
  two failing rows in that file (`the_derived_buffer_is_one_chunk_of_the_group`,
  `a_follower_takes_the_leaders_mark`) fail identically at the merge base — the base tree's `mem_test`
  was built and run to check — so they are not from this change.
