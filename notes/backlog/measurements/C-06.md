- Output parity (merge bar 1): the `greedy` probe (temperature 0, penalties and DRY on) gives byte-identical texts in all
  six runs (sha256 prefixes above identical one for one); steps and tok/step are identical (255 steps, 1.004 and 8.031).
- End to end (merge bar 3): not worse; the differences (+0.2 % c1, +0.4 % c8) are inside the run-to-run spread
  (about 1 %). The gain the item expects, ~15 us of a 14.2 ms step (0.1 %), is below what served tok/s can resolve.
- Targeted traffic (merge bar 2): this lane did not instrument the copy itself. The author's own lane run (PR #193
  comment, 2x R9700 at 210 W, base = tip `6e76ed76`, head = tip + PR) read it at `rad_memcpy_async` with a throwaway
  census: the constant `32 768 + 8 192` B per step (1 row at `max_hist` 8192) disappears for short histories
  (window 5.91 MB -> 4.40 MB), 8 concurrent penalty rows `262 144 + 65 536` B per step -> 0 B constants (window
  30.18 MB -> 9.63 MB), and a row beyond `max_hist/2` uploads the identical full-width constants (byte-identical
  path). That is a deterministic byte count of the upload this item removes; it is credited to the author, not
  re-measured here. The author's served numbers (c1 +1.5 %, c8 +4.7 %) were single runs and are not used.
- Note for the lane: on current tip the fleet container started here without `lora_plain`; the plugin was built into
  both arms' homes anyway (identically) and made no difference to the result.
