# K-01 (dual-weight IQR launch, `latent_in` + shared `gate_up`): CLOSED — the two weights are trellis u5 with different run lengths, so the fused launch is refused at issue and the served model stops

Item as written (backlog K-01, `notes/backlog/optimisation-backlog.md`): "one `iqr_gemv` / `iqr_m16` launch over two
weights and two outputs reading the same rotated int8 codes. Both are u5, K 3072, N 1536, `kw` 8
(`libr4d/r4d_gemm_iqr.hip:954` rule `N >= 4096 ? 4 : 8`, `:1031` for m16), so a concatenated grid is byte-identical.
Plugin: `arch/hyv4flash/hyv4flash_moe.h:390` (`lat_in.step`) and `:399` (`shared.step` -> GatedMlp `:88`)." Why: "`latent_in`
9.2 us + shared gate_up 9.0 us a layer for 2 x 2.95 MB (byte floor 10.4 us at 570 GB/s) … 41 layers x ~6 us = ~0.25 ms of a
13.7 ms pass." Verify: a `r4d_selftest` dual case, the kbench fusion oracle, `layer.py` before/after, and equal greedy text
and logprobs under `RADIANCE_HY4_FUSE_DUAL=0/1`.

This branch built the item in full (commit `36b16cfc`), passed every card-less check and the row-level byte oracle, and
then measured it on the local lane: the pair's two weights are **not** in the same IQR form. `ffn_latent_in` is converted
with `tcq_rows=256` and `ffn_gate_up_shexp` with `tcq_rows=128`, so their form words differ in `lrun` alone; the dual row
requires one form for both, refuses the op at issue, and the served model stops at its first decode step. Nothing is
merged: this run reverts `36b16cfc` and the `scripts/backlog/k01*` lane driver, and leaves this note.

## What the code says (at HEAD, after this branch's revert)

- **The IQR form word carries the trellis run, and the kernel walks it.** `libr4d/r4d_iqr.h:85` `lrun` (log2 rows a run),
  packed at `:91` and read back at `:101`; `libr4d/r4d_gemm_iqr.hip:953` turns it into the launch's column tiles
  (`c.run_tiles = (1u << f.lrun) / 16u`), and `libr4d/r4d_iqr_dec.h:276` uses `run_tiles` to step the trellis state from
  one run to the previous one. One launch has one `FormT`, so one `run_tiles`: two weights with different runs cannot be
  decoded by the same grid.
- **The plugin's form view does not carry it.** `arch/hyv4flash/hyv4flash_common.h:336-340` `CodeForm` is
  `{i8, rot, g8}` and `same()` compares exactly those, so a `latent_in` weight converted with a 256-row trellis run and a
  shared `gate_up` weight with 128 pass the plugin's guard as "the same form".
- **The converter chooses the run per weight.** `rad-info -v` on the model (no GPU needed) prints the recipe of each
  weight: `blk.1.ffn_latent_in.weight … codes=u5 … tcq_rows=256,transform=fwht128` beside
  `blk.1.ffn_gate_up_shexp.weight … codes=u5 … tcq_rows=128,transform=fwht128` — the same u5, the same `fwht128`,
  the same group, a different run.

## The lane

Lane `local` (TP2, cards 0,1, `nospec.yaml`, port 8041), `scripts/backlog/run.sh` phases `c1,c1b,c8,greedy`
(the card's `k01.sh` drove it), `RADIANCE_AQL_STAMP=7`, the item's own A/B: `RADIANCE_HY4_FUSE_DUAL=0` (off) and `=1` (on) on one build, interleaved.

The off arm ran and reproduces the item's basis — c1 13.779 ms/step, 72.6 decoder tok/s (aggregate 70.8), so this is the
model and the pass the item measured. The on arm stopped on both ranks at its first decode step:

```
E rank 1 step 1: kernel gemm_iqr_dual (libr4d, no tunables, device domain) refused op 'gemm_nt_q_dual'
  at M=1 [band M<=16] geometry {N=1536 K=3072 group=128 dtype=i8a8h M=16}: dtype this kernel does not serve
E rank 0 step 1: … the same
```

and the server took the model down with it (`E model hy4-flash: not loaded: it stopped while serving`, then
`W request 2 refused: the engine stopped on an error and is not serving`); the probe's request raised
`HTTP Error 409: Conflict` and the arm wrote no phase JSON, so no c1/c1b/c8/greedy reading exists for it. There is no
before/after stamp pair to report: the fused op never executed.

A dump of the issued operands (a temporary `R4D_DBG_DUAL` print in `r4d_iqr_dual_p`, not kept) shows why, and it is the
same on both ranks:

| operand | tensor | dtype word | decoded |
|---|---|---|---|
| 0, 1 | int8 codes, f32 scales | `0x00000008`, `0x00000001` | `i8`, `f32` |
| 2, 3 | `ffn_latent_in` / its scale view | `0x02310056`, `0x52310056` | trellis-mad `u5`, `L` 16, `lrb` 0, `scale` f32 row, `lrun` **8** |
| 5, 6 | `ffn_gate_up_shexp` / its scale view | `0x01f10056`, `0x51f10056` | trellis-mad `u5`, `L` 16, `lrb` 0, `scale` f32 row, `lrun` **7** |
| 4, 7 | the two bf16 outputs | `0x00000003` | `bf16` |

The words differ in `lrun` and in nothing else — 8 (a 256-row run, `run_tiles` 16) against 7 (128, `run_tiles` 8). The
dual row's `dual_pair` compares the two weights' words and returns `RAD_E_DTYPE` when they differ, which is the refusal
above; and even without that check the two single launches have different `run_tiles`, so the item's premise ("a
concatenated grid is byte-identical") does not hold for this pair. `rad-info -v` shows the same difference without a GPU,
as the recipe's `tcq_rows`.

## What the branch also found, and what a later card needs

- **The plugin's guard is weaker than the row's, and the difference aborts a step instead of falling back.**
  `Lin::declare_dual` compared `CodeForm::same` (i8/rot/g8) and a canonical encoding text, neither of which carries the
  trellis run, so the plugin claimed the fusion and `libr4d` refused it at issue, taking the server down. The run is not
  out of reach at plan time: it is the trellis plane's `block[0]` in the encoding `weight_enc` returns, which is exactly
  what `libr4d/r4d_iqr_layout.cpp:103` turns into `lrun` (`code_form`,
  `arch/hyv4flash/hyv4flash_common.h:344`, drops it). A dual entry must compare there — the two forms, or the packed
  words — and leave the two single launches in place when they differ.
- **The kbench fusion oracle could not reach this op.** `rad-kbench -m --op gemm_nt_q_dual` with the change in place
  reports `0 case(s) checked` and lists the row under *Rows nothing ran* (`gemm_iqr_dual` -> `gemm_nt_q_dual`: declared,
  never given a case); the unfiltered `rad-kbench -m` did not finish inside the window (stopped after 24 min on a box at
  load ~60, so it left no report). The item's second oracle has no reading here and needs a case recipe for the op before
  it can say "byte-identical".
- **K-02..K-04 (the other dual entries) must check the pair's run first.** Any pair whose two weights were converted with
  different `tcq_rows` is refused for the same reason; `rad-info -v <model> | grep ffn_latent_in` and the same for the second
  weight answers it in a second, before any kernel work.
- **The two ways this item could be made to pay, both outside its scope.** Re-convert `ffn_gate_up_shexp` with
  `tcq_rows=256` so the pair shares a form — a conversion change (§4 out of scope) that rewrites the weight's code
  stream, so it is a lossy change needing KL against today's default, not this lossless item. Or carry two forms in the
  kernel (two `run_tiles`, two form tables), which is a different and much larger change than "same junction codes".
